## 条目模板：菜单式，三档（2026-10-08 定案）

**不是每条都套 14 段。** 段是菜单，按「有没有料」点，**没料就跳过，不许写「本节不适用」**。

### 必写 4 段（每条都要）

| 段 | 判据 |
| --- | --- |
| **它是什么** | 必须能被判真假。写「支持 X」是评价，写「`bEnableX` 默认 false」才是断言 |
| **怎么用** | 至少给一种写法（`.dui` / C++ / 蓝图）。纯配置项可只给取值表 |
| **什么时候它不好用** | 有边界就写；确实没有边界时，写清「为什么它没有边界」 |
| **接着往下读** | 至少要有一个**具体可行动链接**（参考页 / 手册 / 在线文档 / 源码） |

### 有料才写（缺料直接跳过）

| 段 | 什么时候写 |
| --- | --- |
| **一个控件由哪几块拼起来** / 结构与组成 | 该功能有多个部件或分层时 |
| **字段表 / 参数表 / 取值表** | 有结构化枚举时（默认值必须列全） |
| **与 UMG 的对照** | 有对应者时才写。参考页末尾的 `## Compared with UMG` 表是主要来源 |
| **它换来了什么** | **只在能说出「改了什么 → 换来了什么 → 出处」时写。** 写不出出处就是评价，不写 |
| **出问题先查这几处** | 有具体症状→排查项时。这是症状表，不是常识清单 |
| **还没核实的** | 有未核项时。宁可写「未核」也不要写猜测 |

### 三档用法

| 档 | 用在 | 典型段数 |
| --- | --- | --- |
| **T1 域级** | 如 #1 控件基类、第 4 组视觉、第 11 组控件库、第 19 组 `.dui` 语言 | 12–14 |
| **T2 具体类型 / 功能** | 如 #2 锚点数据、#3 视觉槽、单个控件 | 7–9 |
| **T3 单点开关 / 属性** | 如单个 `RenderScale`、单个取值 | 3–5，且常常**合并进所属条目**而不单独成篇 |

⚠️ **不写「优势」节** —— 理由见下表。
| ⚠️ 不设「优势」节 | **刻意不加。** 理由：①优势是评价性内容，文体禁止最高级自夸与能力夸大；②它会被「与 UMG 的对照」和「什么时候它不好用」重复两遍；③优势是相对的（从 UMG 来 vs 从 uGUI 来，感受相反），通用写法对谁都不中。**改用「它换来了什么」**：只写作者**写明了理由**的设计取舍，每行可回指出处 |
| ⚠️ 「它换来了什么」只在**域级**条目写 | 子功能条目（如 `TabIndex`）没有设计取舍可谈，硬凑会灌水。判断标准：能不能指出「改了什么 → 换来了什么 → 出处」 |
