## 这一章讲什么

前 25 章讲的都是**插件本身**：控件、视觉、行为、布局、`.dui` 语言、渲染、输入、编辑器设计器。本章换到**围绕插件的工具** —— 那些不随插件一起发出去、却决定「它能不能被信」的东西。

它们大多不在 `Source/`，而在仓库根与 `Tools/`。按用途分三组，比按清单顺序清楚：

| 组 | 工具 | 回答的问题 |
| --- | --- | --- |
| **质量门** | 测试宿主（#302）、测试运行（#303）、覆盖矩阵（#304）、静态检查（#305）、模块所有权表（#306） | 「这次改动能不能进」 |
| **对拍与基准** | 文本对拍（#307）、基准（#308） | 「它画得对不对、动起来贵不贵」 |
| **编辑器辅助** | VS Code 扩展（#301） | 「写 `.dui` 时手边有什么」 |

一句话概括这三组的关系：**质量门**把一次改动变成一个能读的判定；**对拍与基准**把它的「对」和「贵」摆到可核对的东西旁边；**编辑器辅助**把语言搬进写代码的地方。

## 质量门

五个部件各管一段，合起来把「我改了它」变成「它到底行不行」。

### 测试宿主：一个只为插件存在的项目（#302）

`Tools/TestHost/` 是**一个最小的 Unreal 项目**，存在的唯一目的就是构建 DreamGUI、跑它的自动化套件 —— 和你真正在做的那个项目分开。

README 把「为什么分出来」说成三条成本：工作项目的编辑器得先关掉（构建要替换插件的 DLL，开着的编辑器占着它，还会和测试共用 `Saved`）、别的会话会改到同一份检出、以及 **「项目能构建」不等于「插件能构建」** —— 一个恰好开了别的插件、带自己配置的项目，会掩盖插件忘了声明的依赖。

它的做法是：`Plugins/DreamGUI` 是 DreamGUI 仓库的一个**独立的 git worktree**，有自己的 `Binaries/` 和 `Intermediate/`；只启用 DreamGUI 和 Enhanced Input；除了两个冒烟探针没有自己的代码，除了旧资产夹具没有自己的内容。所以它构建和运行时**你的编辑器可以开着**，而且它证明的正是「插件能单独构建」。

`Tools/TestHost/Template/` 是宿主的模板，`New-DreamGUITestHost.ps1` 按模板建出一个宿主，可重复运行（缺的补上、一样的不动、不一样的**列出来保留**，`-Force` 才替换、旧文件留一份 `.bak`）。宿主每次运行都加载**旧资产夹具**：插件在 1.0.0 保存的 widget Blueprint 和一个关卡 —— 之后的版本都要能继续加载的基线 —— 外加保存时它们的快照，一个没有重定向就改了名或搬了家的类会在这里现形。夹具是**输入，永远不是输出**：写夹具的命令拒绝覆盖已存在的夹具。

宿主还带两个冒烟探针：一个**点击冒烟**（把鼠标事件交给 `FSlateApplication` 自己的入口点，走完整条从平台消息到按钮的路）和一个**打包文本冒烟**（在烹饪打包的游戏里跑一屏文本用例，和未烹饪的同一份构建逐字段对比）。⚠️ **打包文本那一个连着打包与字体那条线，细节留给下一章。**

### 测试运行与预设（#303）

日常用的是 `Tools/Tests/Invoke-DreamGUITests.ps1`：它一次做完**预检、静态检查、构建、模块清单校验、编辑器运行、判定**，并告诉你到底跑了多少条测试。它需要 PowerShell 7.2+、`PATH` 上的 Python 3.8+、以及 git。

最简的一条路是引擎自带的命令行：编辑器控制台里敲 `Automation RunTests DreamGUI`，或者加 `-ExecCmds` 无头地跑。`RunTests` 的过滤器按 `+` 拆、各项取或：`StartsWith:X` 匹配以 `X.` 开头的名字，`^X$` 精确匹配，`Group:X` 展开 ini 里的组，其余是不分大小写的**子串**。

运行器自己维护一组**预设**（`Tools/Tests/presets.json`，不依赖引擎的 ini 组）。每个预设定四件事：选哪些测试、给编辑器什么参数、**下限**（至少要真跑多少条）、超时。

| 预设 | 跑什么 | 编辑器参数 |
| --- | --- | --- |
| `Quick` | 除 PIE 层外的全部 `DreamGUI.*` 与 `DreamTween.*` | `-nullrhi` |
| `Interaction` | `Private/Interaction` 与 `Private/Driver/Tests` 下声明的测试 | `-nullrhi` |
| `Designer` | `DreamGUI.Designer.*` | `-nullrhi` |
| `Rhi` / `Validate` | 标了 `NonNullRHI` 的（PIE 层与基准除外）/ 同上并开 RHI 验证层 | `-RenderOffScreen` |
| `Pie` / `PieRhi` | `DreamGUI.Pie.*` / 其中 `NonNullRHI` 的那些 | `-nullrhi` / `-RenderOffScreen` |
| `Exit` | `DreamGUI.Lifecycle.Smoke.*`，然后编辑器自己退出、事后搜日志 | `-nullrhi` |
| `Perf` | 基准 `DreamGUI.Performance.*`，独占一个编辑器 | `-RenderOffScreen` |
| `All` | 全部，一个编辑器、真 RHI | `-RenderOffScreen` + 关掉 GPU Scene 预留缓冲 |

`-nullrhi` 下引擎自己会丢掉所有标了 `NonNullRHI` 的测试，所以无头预设不用去排除像素测试。**下限**是挡住「测试模块没加载、于是 0 条测试 0 条失败冒充通过」的那道闸，只升不降。套件的规模是几千条 —— `All` 预设的下限是 **2726** 条、`Quick` 是 **2430** 条（`presets.json` 里 `minTests` 的字面值）。

⚠️ 一处要留意：`Tools/Tests/README.md` 里那张预设表的下限与超时**比 `presets.json` 旧**（它写 `Quick` 1386、`All` 1404）。**以 `presets.json` 为准** —— 运行器读的是它，README 那张表待修。

### 判定与退出码（#303）

一次运行由 `Tools/Tests/digest.py` 判定。它从引擎的 JSON 报告与 `run.log` 里读出报告说不出来的东西：ensure、崩溃、加载失败的插件、匹配不到东西的过滤器、一直没清空的队列，并把「实际跑了哪些」和「源码声明了哪些」对照 —— **一条该跑没跑的声明测试**说明二进制比源码旧、或有模块没加载。

退出码只有三个：

| 码 | 含义 |
| --- | --- |
| `0` | 绿：跑了的测试全过（已知问题除外） |
| `1` | 红：至少一个不在已知问题里的测试失败 |
| `2` | **没法判定**：静态检查、构建、清单、崩溃、ensure、超时、缺报告、少于下限，或编辑器以非零码退出 |

**有 ensure 的运行不算绿**，即使每条测试都过了 —— ensure 是测试没断言到的 bug。报告落在 `Saved/DreamGUITestReports/<时间戳>-<预设>/`，要读的是 `summary.md`：结论、计数、每个失败和它的第一条错误、已知问题、ensure、崩溃、慢测试与不稳定的测试。

### 覆盖矩阵：测到了是量出来的（#304）

「测到了」是**量出来的，不是感觉出来的**：每个可交互的控件或行为，乘上玩家触达它的每种方式和它出厂的每种配置，是一张表的格子 —— 每格要么被一个驱动测试覆盖、要么声明不适用并给出理由、要么是个洞。

- **行**是控件与行为：`Source/DreamGUI*/Public/Controls/*.h` 与 `Public/Interaction/*.h` 里的 `UCLASS`（每个模块都算），在 `Tools/Tests/coverage.json` 里分组与过滤。一个既不在行、也不在排除名单里的类会以一个**未分类**行出现、满格是洞，所以新控件混不过去。
- **列**是输入 × 配置：输入 `[Pointer]`（鼠标）/ `[Touch]`（触摸）/ `[Nav]`（手柄与键盘导航）/ `[Text]`（键盘文本），配置 `[Animated]`（出厂、动效开着）/ `[Disabled]` / `[Scaled]` / `[World]`。

测试在声明之后、用**同一个全名**登记标签（`REGISTER_SIMPLE_AUTOMATION_TEST_TAGS`）；框架按给出的名字归档，打错字会**静悄悄**归到一个不存在的测试下。`coverage_matrix.py` 画这张表，`--fail-on-holes` 让它成了一道闸。

### 静态检查：构建之前的一批便宜检查（#305）

`Tools/Tests/static_checks.py` 跑在**构建之前**，两类：

- **UHT 与 MSVC 形状的**：抓会让构建停下的东西（同名的第二个反射类型、遮住祖先的 `UPROPERTY`、插件当引擎插件编译时缺 `Category` 的公开成员、override 上的 `UFUNCTION()`）。
- **测试自己的约定**：名字形如 `DreamGUI.<Area>.<Sentence>`、带 `EditorContext`、标签来自覆盖词汇表、没有 `NonNullRHI` 的像素测试、`BindTest` 到处都用、注释和字符串里不许有计划标签。

它同时管**模块分层**：`module-owners.csv` 说每个文件归哪个模块，一个文件只能包含自己模块和更低层的头文件，不能包含更高层或同层兄弟的（`layering`）。仍然这样做的包含列在放行名单 `Tools/Tests/layering-allow.json` 里，**这张名单只减不增** —— 一条已经消失的边留在名单上本身就是错误（`layering-stale`）。另一条 `engine-private-path` 把引擎的 `Private` / `Internal` 目录挡在每个模块的包含路径之外。

一条应当保留的发现可以就地放行（写在那一行或上一行：`// static-checks: allow(<规则>) <理由>`），或写进放行名单 `Tools/Tests/static-checks-allow.json`（路径 glob、可选正则、理由）。用 `--list-rules` 打印每条规则和它的理由。

### 模块所有权表：权威的一列（#306）

`Tools/Tests/module-owners.csv` 是「**每个运行时文件归哪个模块**」的权威表 —— 约 55 KB，表头是 `path,module,reason`。它是分层的输入：`layering` 规则照着它判谁在谁上面；`Tools/ModuleSplit/` 的搬迁脚本按它 `git mv` 文件、改导出宏、更新它自己。

它同时是**契约**：一个文件移动或新增，要在**同一次改动**里补上它的行。表里出现的模块是 `DreamGUIRenderer`（最底）、并列的 `DreamGUI` / `DreamGUIInput` / `DreamGUIControls` / `DreamGUIExtensions`、以及最上面的 `DreamGUISamples`；没被列出的文件，归属它所在的那个模块。

⚠️ `Tools/ModuleSplit/`（搬迁脚本：`move_module_files.py` / `moved_types.py` / `retarget_script_paths.py` / `check_game_includes.py`）**不在功能总清单里单独列项**，但它就在这条线上 —— 已记进缺口。

## 对拍与基准

### 文本对拍：DreamGUI / Slate / Chrome 同一语料（#307）

`Tools/TextParity/` 把**同一份文本语料**交给三方画，再逐项比：

- **DreamGUI**，在 `DreamGUI.RHI.TextParity.<case>` 里，用同一个用例的字体文件做距离场字体；
- **Slate**，同一个测试里，走 `FSlateTextLayout`（`STextBlock` 排版用的那套）；
- **Chrome**，由 `Make-ChromeReference.ps1` 在测试之前画好、和语料一起入库。

语料 `Source/DreamGUITests/Resources/TextParity/corpus.json` 列出每个用例的字体、字号、盒子宽、行高、字距、语言、方向和排版对齐 —— 字距、连字、字号梯子、小字、零宽字符、CJK 与回退面、双向文本、泰文、天城文、彩色 emoji、组合记号、长词、标点、富文本、两端对齐、制表位、渐变填充…… 运行写出图与数：每方的图、三方并排的对照图、角落用例的掩膜、每个用例的数、以及一份 `report.json` / `report.md`。

比什么：**行首**（行从哪个 UTF-16 偏移开始）、**caret**、**首行基线**、**行距**、**墨迹**（与纸面相距足够远的像素边界，以及线性光下的墨迹总量）、**锐度**（每笔画的边缘宽度、灰度占比、每单位墨迹的梯度 —— 小字按这个判），以及角落用例的**掩膜差异**、渐变填充用例的**上色对比**。断言按用例在 `corpus.json` 里点名；`reference` 为 `slate` 的用例对着 Slate 比（Chrome 没有中省略号）。

⚠️ **Chrome 参照要随语料重跑**：拿一份旧语料做的参照，比的是错的文本。

### 基准：两面「按钮墙」（#308）—— 本轮未跑

`Tools/Bench/` 是性能工作所用的基准：**两个场景，各是某一类 UI 的最坏情况**，在测试宿主上跑，用编辑器的 PIE 或编辑器二进制的 `-game` 进程。

| 模式 | 场景 |
| --- | --- |
| `screen` | 一个屏幕空间画布上 **5000 个按钮**，点它的 Play 后全部一起转，一轮接一轮 |
| `world` | 一个关卡里 **2688 个世界空间按钮面板**，每个都是自己的 actor 和画布、各自动画 |

⚠️ **这两个场景不在仓库里** —— 它们是使用 DreamGUI 的项目的内容、不是插件的，跑之前要拷进宿主的 `Content`（屏幕墙用 `-ScreenWidget` 指定 widget 类，世界墙用 `-Map` 指定关卡）。

怎么跑：`bench_launch.ps1` 跑一次会话，`bench_series.ps1` 跑多次并把每次的中位数并进一份报告；开关有 `-Mode`、`-Game`、`-Map`、`-ScreenWidget`、`-Csv 1`、`-Trace 1`、`-StatsCmds`、`-AbCmds`（A/B：先测 A，跑几条命令，再测 B）…… 产物全进 `<host>/Saved/DreamGUIBench`。读 profile 与 trace 的脚本也在那里：`csv_summary.py`（各列的中位数/平均/p95）、`csv_spikes.py`（超出预算的帧）、`insights_top.py`（一份 trace 里最重的计时器）、`frame_breakdown.py`（最慢的几帧逐帧拆开）。

⚠️ **本轮没有跑过它**，所以本章只讲**有哪些场景、怎么跑**，**不给任何结果数字** —— 按既定口径，成本只写质性的。读数还有几条规矩值得先记住：**丢掉构建后的第一次启动**（着色器在后台编译，那一次更慢）、**只在同一次坐下里比较**（不同天、或机器上任何东西变过之后的数不能比）、**trace 本身要花帧时间**（测量的会话不带 trace）。

## 编辑器辅助：VS Code 扩展（#301）

`dreamui-language-support` 是**一个独立的仓库**（不在插件里，插件 README 只连到它）。它的 README 说它为 `.dui` 提供：

| 能力 | README 的说法 |
| --- | --- |
| 高亮 | 整个语法的高亮，外加**语义高亮**（节点 id 按它变身的成员变量着色，样式按类，资源按只读常量，`->` 事件与处理函数，循环变量……） |
| 补全 | 内建标签、布局容器、组件类、逐类属性、枚举值、槽属性、资源类型、`@` 资源引用、`->` 事件名 |
| 悬停 | 属性的类型与枚举值；组件语法里还给出别名解析到什么、`emit` 的签名、无名节点编译出的 id |
| 跳转 | `@Name` 与样式用的**转到定义**、`use … as` 到目标、`ns.Label` 到库、槽填充到组件的槽；树的大纲；精确折叠与智能选择 |
| 诊断 | 用**编译器自己的码**与措辞、按编译器自己的严重级 |
| 格式化 | 按块深度缩进、`=` 与箭头两侧各一个空格、`}` 独占一行 —— 和设计器写回打印的是**同一套写法**，所以两者不打架 |

它还有一行要点和本章其余部分相接：Unreal 设计器的工具栏 / 层级右键菜单里有 **Reveal in VS Code**，跳到 `.dui` 里节点所在的那一行。

⛔ **不推断实现**：README 说它读插件写出的符号（编辑器启动时、或命令 `DreamUI.ExportSymbols`，写出 `DUI/.dui-symbols.json`），并说「编译器是权威」。**本节只照它的 README 说它做什么，不说它怎么做。**

## 怎么用

从「改了一处」到一个能信的判定，最短的一条链：

1. 无头跑一遍：`pwsh -NoProfile -File Tools\Tests\Invoke-DreamGUITests.ps1`（默认 `Quick`）。换预设用 `-Preset <名字>`；只重跑不重编用 `-NoBuild`。
2. 编辑器开着、不想关：指向测试宿主（`-Project <host>\DreamGUITestHost.uproject`），宿主会自己构建自己的 worktree。
3. 改了控件或输入行为：跑 `Designer` / `Interaction` 预设，再看 `Tools/Tests/COVERAGE.md` 那张表有没有新洞。
4. 改了文本：跑 `Rhi`，看文本对拍报告；改了渲染器：用 `Perf` 预设的渲染基准，或 `Tools/Bench` 的两面墙（**本轮未跑**）。
5. 写 `.dui`：装 VS Code 扩展，配一个 `DUI/` 目录。

## 什么时候它不好用

- **测试宿主测的是它 worktree 里已提交的内容。** 你工作副本里未提交的改动（改过的材质、没保存的资产），在它 commit 并检出过去之前，宿主看不到。
- **宿主第一次构建要把整个插件编进它自己的 `Intermediate/`**，要花时间、要占宿主的盘。
- **已存在但与模板不一样的文件，默认只列出来、不替换**（`-Force` 才换，还会留一份 `.bak`）。这是保护，不是 bug。
- **静默的失败是最贵的一类，所以到处是下限和清单。** 测试模块没加载会以「0 条测试 0 条失败」冒充通过，所以预设都有**下限**；一个模块漏进清单会让整个插件加载失败；一条该跑没跑的声明测试会让运行直接算「没法判定」。
- **基准只能在同一次坐下里比。** 不同天、机器上任何东西变过之后，数不可比；构建后的第一次启动要丢掉。它也不是回归闸门：README 明说「没有任何东西会因为时间而失败」。
- **VS Code 扩展是一个独立仓库。** 它跟插件、跟引擎各自演化，不是插件的发布物。
- **`.dui` 是它和设计器共同的前端。** 两个都改同一个文件，但只有一套写回规则（§7 / §9）；扩展的格式化也照着设计器写回来。

## 还没核实的

- **`Tools/Bench` 本轮没跑过**（清单原文「本轮未跑」）：本章只有场景与跑法，**没有任何性能数字**。
- **`Tools/Tests/README.md` 的预设表 vs `presets.json`**：README 的下限（`Quick` 1386、`All` 1404）与超时比 `presets.json`（`Quick` 2430、`All` 2726）旧。本章按 `presets.json` 写，README 那张表待修。
- **测试没有「通过数」** —— 只有下限（一个定义数），没有任何通过数。
- **`Tools/ModuleSplit/` 与 `Tools/Tests/COVERAGE.md` 不在功能总清单里单独列项**，但读下来都在本章这条线上，已记缺口。
- **VS Code 扩展不推断实现**：只按它的 README 写它提供什么。
