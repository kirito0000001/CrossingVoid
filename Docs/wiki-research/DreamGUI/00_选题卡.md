# 00 · 选题卡 — DreamGUI 功能全景

> L0，刻意短。本文件是采集的准入闸门；下面第 ② 句答不出就不该开工。

## 五问

**① 读者是谁、他正在干什么？**
晓桀本人（独立开发者 / 美术，Unreal 项目 CrossingVoid 的作者）。他刚把 DreamGUI 插件放进自己项目的 `Plugins/`，准备为它写一份**最详细的介绍文档**。此刻他手上同时有插件源码和官方 wiki，但还没系统读过。

**② 他要拿这篇干什么？**
当成**功能地图**用：先知道这套插件到底有哪些功能域、每个域里有什么，再决定后续「逐个功能深挖」的顺序与深度。这一轮**不下笔写介绍文档**，只把可引用的事实底座搭起来。

**③ 要回答哪 3–7 个问题？**（账本分组主键）

| Q | 问题 |
| --- | --- |
| Q1 | 这是什么：定位、来历（LGUI 血脉）、许可、版本、平台真相、迁移路径 |
| Q2 | 代码基座：有哪些模块、怎么分层、规模多大、编辑器侧与工具链有什么 |
| Q3 | 核心能力域：控件模型 / 画布 / 世界空间 / 布局 / 文字 / 渲染 各自提供什么 |
| Q4 | 控件库与样式：有哪些控件、哪些行为组件、样式体系怎么组织、和 UMG 怎么对照与互操作 |
| Q5 | `.dui` 语言与诊断：语言能表达什么、写回机制、诊断码体系 |
| Q6 | 动画：补间、控件动画、时间轴、布局动画、文字动画各有什么 |
| Q7 | 输入与键位导航：每玩家输入、射线命中、Tab/手柄导航、弹层与模态、操作提示栏 |

**④ 明确不写什么？**
- 不写教程步骤（安装、第一个界面怎么做）—— 那是官方 wiki `start/` 的活。
- 不写逐类 API 参数表 —— 那是 `Docs/Reference/` 与 wiki `reference/` 的活，账本只记「存在 + 定位」。
- 不写性能实测数字 —— 本轮**没有跑**任何基准（`Tools/Bench` 存在但未运行），第三方来源的数字一律标 `二手线索`。
- 不写「作者意图 / 为什么这么设计」的推测 —— 拿不到一手口述就进缺口清单。

**⑤ 文体？**
技术介绍文档（长文 / README 体）。目标读者是**中文的 Unreal 使用者**，术语沿用插件自己的中文译法（视觉 / 画布 / 行为 / 槽 / 锚点 / 轴心）。

## 硬约束

- **只读采集**：被采对象是 `C:\CrossingVoid\Plugins\DreamGUI`（独立 git 仓库）。本专题**不在插件目录内建任何文件**，也不在插件上跑任何构建 / 测试。
- **本轮范围**：只做「有什么」的全景，不做「怎么用」的展开。深挖留给后续专题。
- **两个源并行**：插件仓库（一手代码）＋ 官方 wiki（一手文档）。两者都是官方产物，冲突时**记矛盾不擅自裁定**。
