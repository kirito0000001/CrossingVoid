## 零、这一页是干什么的

一句话：**打包前，确认"这次要发的东西"没问题。**

用户原话（本设计的验收基准）：

> 「常规补丁阶段最主要就是这个：确认一下这次新增的内容没有问题。
> 大版本更新的时候会让补丁正规化，这时候也需要确认。」

所以它不是"打包按钮页"，而是**打包前的检查台**。打包本身还是 `Tools\Pack-CrossingVoid.ps1` 那条命令。

配套的目标是**防失误**，不是看新鲜：

> 「你这次只动了 3 个角色图，结果面板说 chunk3 新增了 500 个文件 —— 那就是有东西误入或误删了。
> 它回答的是『这次改动和我的预期一致吗』。」

## 一、两条路（模式差异，这是全篇的骨架）

用户从最开始设计这个插件时就分了两条路，本页沿用：

| | **常规补丁** | **大版本更新** |
| --- | --- | --- |
| chunk 号 | 沿用；新内容自动拿新号（= 当前最大号 + 1） | **整份重排**，补丁期的号作废（用户原话：「补丁的顺序就作废了，按照新的排序来」） |
| 判定"哪些是新增" | 和**上一次发布报告**对比 | 和**上一个大版本基线**对比 |
| 未分类内容 | **只提醒**（可以照常打包，它会进新的补丁 chunk） | **强制清空**：还有未分类就不让打包 |
| 一键指派 | 可选（顺手用） | **必备**（正规化的主要动作） |
| 玩家侧代价 | 只下变化的包 | 全量重下（号重排 → 本地缓存全失效，这是大版本的预期行为） |

> 「普通补丁只提醒；只有大版本正规化模式下才强制」—— 用户确认。

## 三、每栏的数据从哪来（**关键，决定要存什么**）

### 3.1 两个数据源

| 数据 | 来源 | 什么时候有 |
| --- | --- | --- |
| 规则（chunk / 名字 / 目录 / 备注） | `Config\DefaultCrossingChunk.ini` | 随时（编辑器里改，右键菜单和本页写同一份） |
| 真实结果（体积 / 命中文件数 / 未分类清单 / 变化） | 打包脚本产出的 **`chunk-report.json`** | 每次打包后 |

**没打过包时**：页面只显示规则本身（号、名字、目录数）+ 标注「还没有报告，跑一次打包才有体积和变化」。可选增强：用编辑器的 AssetRegistry 估一个"资产数"，但**体积一律不估**（估不准会误导）。

### 3.2 `chunk-report.json`（打包脚本产出）

存到 `Saved\PackLogs\ChunkReports\<平台>\<时间戳>-<模式>.json`，同时把"最近一次"复制成 `latest.json`。
**实际路径带目标**：`ChunkReports\<平台>-<目标>\`（如 `Win64-Client\`），因为同一个规则在客户端/服务器上的命中完全不同。
体积约 800 KB（里面存了全部文件的归属，用来做跨版本对比；比设计初稿估的"几十 KB"大，但换来的是精确的差异）。

```jsonc
{
  "schemaVersion": 1,
  "generatedAt": "2026-09-19T01:20:33+08:00",
  "mode": "Quick",              // Quick | Base | Patch
  "platform": "Win64",
  "project": "CrossingVoid",
  "engine": "5.8.2",
  "previousReport": "20260918-2354-Quick.json",   // 对比对象；没有就 null

  "chunks": [
    {
      "id": 3,
      "name": "第三章-角色与主界面",
      "kind": "rule",            // rule | unclassified（未分类桶）
      "folders": ["/Game/AssetMaterial/ImageS/CharaterS", "..."],
      "matchedFiles": 991,       // 打包日志里 "Pak rule ... with N matching files"
      "packages": 991,           // IoStore 报告里的包数
      "bytes": { "pak": 0, "ucas": 234200000, "utoc": 320000, "total": 234520000 },
      "delta": { "added": 12, "removed": 0, "modified": 3, "bytes": 12680000 }
    }
  ],

  "unclassified": [
    { "folder": "/Game/AssetMaterial/FXs/触地灰尘", "files": 9, "bytes": 1258000, "isNew": true }
  ],

  "issues": [
    { "level": "warn", "code": "EmptyRule", "target": "chunk5",
      "message": "chunk5「材质」这条规则一个文件都没命中" }
  ],

  "download": { "changedChunks": [3, 8], "bytes": 19820000 }
}
```

几个字段的取法（都在现有产物里，不用新增 cook 逻辑）：

- `matchedFiles`：打包日志里 `Pak rule 'CC_xxx' with N matching files`
- `packages` / `bytes`：IoStore 报告段（`LogIoStore` 的容器表）+ `D:\Build\...\Paks\` 里的文件大小
- `unclassified`：把本次 staged 清单（`PrePak_<平台>_UFSFiles.txt`）按同一套规则链跑一遍，
  取到 `CC_NewContent` 的那些（就是现在的 63 个文件 / 6.8 MB），按目录聚合
- `isNew`：拿 `previousReport` 里的文件集合比对 —— 上次没出现过的目录 = 真新增；出现过 = 老欠账
- `delta` / `download`：和 `previousReport` 做文件级 diff 得出

### 3.3 历史报告

- 每次打包都存一份，只增不删，可以翻历史、挑任意一份做对比
- 每份几十 KB（只存"文件路径 + 所在 chunk + 大小"的压缩列表）
- **AxTools 以后读的是同一份 json**，不重复实现一遍规则匹配
  （这符合之前定的原则：打包脚本产出机器可读结果，AX 只读不猜）

## 四、体检清单（自动跑，不设按钮）

打开页面时跑一遍，"重新体检"只是手动再来一次；**发现问题只提示、不阻断**（用户确认「提醒就行」），
**唯一例外是大版本模式下的未分类**（见第一节）。

| 代码 | 触发条件 | 级别 | 文案 |
| --- | --- | --- | --- |
| `RuleFolderMissing` | 规则里的目录在工程里不存在 | 警告 | 「chunk3 里的 `/Game/AssetMaterial/ImageS/CharaterSS` 不存在（是不是改名了？）」 |
| `EmptyRule` | 规则 0 命中（打包报告里的 `matchedFiles == 0`） | 警告 | 「chunk5「材质」一个文件都没命中」 |
| `DuplicateFolder` | 同一目录被两条规则认领 | 警告 | 「`/Game/Art/Sound` 同时属于 chunk1 和 chunk6，目前按号小的算」 |
| `RuleOutsideGame` | 规则目录不在 `/Game` 下（生成器翻不出掩码） | 警告 | 「`/MyPlugin/X` 不在 /Game 下，这条规则不会生效」 |
| `UnclassifiedNotEmpty` | 有未分类内容 | 补丁：提示 / 大版本：**阻断** | 「还有 6.8 MB 未归类；常规补丁会被打成新 chunk，大版本必须先指派」 |
| `ChunkIdReused` | 复用了一个已经发过包的号（可选） | 提示 | 「chunk7 已经发过包，这次内容换了，玩家会重下它」 |

## 五、大版本的"正规化"流程（用户描述 + 我的细化）

用户原话：

> 「一般来说，新增的资源其实已经就在 chunk 大分类里面了……所以正规化的时候基本可以一键指派，
> 如果有真的没有办法自动分类的，得提醒指派，强制的，因为走的就是大版本更新的路。」

流程：

1. 切到**大版本更新**模式 → 页面列出「补丁期临时 chunk」和它们里面的目录
2. **一键指派**：按**上一次大版本基线报告里的文件归属**，把这批目录归回它原来所属的正式 chunk
   - 依据是历史报告，不是猜的：这些文件上次在 chunk3，就归回 chunk3
   - 找不到历史归属的（真的是全新目录）→ 进第 3 步
3. **强制人工指派**：清单没清空就不让打包（大版本走重发全量的路，不该有归属不明的东西）
4. **重排号**：正式 chunk 从 0 起重新编号，补丁期的号清空，写回规则文件
   - 这会重新生成整份 `DefaultChunkRules.ini` 的规则行
   - 玩家侧：号重排 = 本地缓存全失效 = 重下全量（大版本本来就该这样）

> ⚠️ 第 4 步是**破坏性**的（号会变），所以：执行前先把当前规则文件备份一份，
> 并在页面上明确提示"这一步会让玩家重下全量"。

## 六·补、执行与日志：为什么仍然走脚本，但要在编辑器里能看到

用户的问题（2026-09-19）：

> 「我看你是走脚本打包吗？那我这样子是不是不能在虚幻的日志里看到实时状况啊，要不要改一下？
> 之前做了一些项目也是感觉插件内比脚本更稳定一些」

### 先摆事实

1. **现在的链路**：`Tools\Pack-CrossingVoid.ps1` → `RunUAT.bat BuildCookRun` →
   另起一个 **`UnrealEditor-Cmd.exe -run=Cook` 进程** 去 cook，再由 UAT 做 stage/pak。
   所以 cook 的日志天然不在编辑器 Output Log 里——**它是另一个进程**。
2. **日志其实一直在**：脚本把全部输出同时写 `Saved\PackLogs\pack-<模式>-<平台>-<时间>.log`，
   并且脚本自己也会在"产物盘点"里打出容器体积表。（排查时一直在用这份文件。）
3. **官方"打包项目"（平台菜单里那个）也是走 UAT BuildCookRun**，只是外面套了 Project Launcher 的界面。
   也就是说：**"插件内"和"脚本"在流水线上没有区别**，区别只是"谁调用、日志显示到哪"。
4. **更硬的一条**：我们的分包链路（`-RunChunkAssigner` 的 oplog 分配、
   `DefaultPakFileRules.ini` 的逐文件覆写、ZenServer）**全部发生在 UAT 的 stage/pak 阶段**。
   所以打包**必须经过 UAT**，插件只能"调用它"，不可能"替换它"。

### 结论：流水线不动，补"执行 + 实时日志"

真正常见的"插件内更稳"体验差异，来源其实是这三件事，而不是宿主本身：

· 进程环境（工作目录、PATH、编码、中文路径） · 参数拼装 · 前置步骤有没有固化。

前两件我们的脚本已经踩过并修掉了（`-target=` 缺失、`-client` 冲突、PowerShell 编码、
UTF-8 无 BOM 读写规则文件）；第三件也已经固化在脚本里（**打包前跑规则生成器**、
**确保 ZenServer 常驻**）。所以"稳定性"这一项现在没有提升空间——**换成插件里重写一遍反而会引入两套实现漂移**。

于是本页的做法是：

```
页面上的「开始打包」按钮
   └─ 插件用 FPlatformProcess::CreateProc 起同一个脚本（同一套参数）
        ├─ 子进程 stdout/stderr 实时 pipe 回来 → 显示在页面下方的日志区
        └─ 脚本自己照旧写 Saved\PackLogs\pack-*.log（历史可查、AX 也能读）
```

好处：

- **编辑器里能实时看**（这就是你要的），而且日志区和打包产物一一对应；
- 命令还是那一套：AX 调、命令行调、页面调，**三条路同一条命令**，不会出现"页面打出来的包和脚本不一样"；
- 官方"打包项目"入口不使用：它会丢掉我们那两件前置（规则生成器、ZenServer 常驻），
  除非以后做成自定义 Project Launcher profile + 把 ZenServer 装成服务——那是另一个话题，现在不做。

### 日志区的两条设计

- **默认全量实时**（原样 pipe，不做过滤）——排查时最怕"日志被写日志的代码吃掉"
- **打包结束后额外给一份摘要**（就是脚本现在打印的那几块）：各容器体积、每条规则的命中文件数、
  体检结果、以及"玩家本次需下载多少 MB"。这样不用在几万行里翻关键信息。

### 顺带说明：页面的三个按钮各自干什么

| 按钮 | 行为 |
| --- | --- |
| 开始打包 | 跑 `Pack-CrossingVoid.ps1`（参数由页面上的模式/平台下拉决定），日志进日志区 |
| 复制命令 | 只把命令行复制出来，方便在终端里复现（排查时最有用） |
| 打开日志目录 | 打开 `Saved\PackLogs\` |

## 九、不做（留档，别走回头路）

| 想法 | 为什么不做 |
| --- | --- |
| 在页面里让用户改 chunk 号 | 号是下载器认的稳定标识，改了会让已发布的包对不上；要改只在"大版本重排"这一步统一改 |

### 11.1 现状

| 参数 | 可选值 | 说明 |
| --- | --- | --- |
| `-Platform` | `Win64` / `Android` | 产物目录 `Windows\` / `Android\` |
| `-Target` | `Client` / `Server` / `Both` | Client → target `CrossingVoid`（`-clientconfig=Shipping`）；Server → target `CrossingVoidServer`（`-serverconfig=Shipping -server`）；Both → 跑两次，产物分目录 |
| `-Mode` | `Quick` / `Base` / `Patch` | 基线会落到 `<工程>\Releases\<版本>\<平台[-Server]>\`，Base 不允许覆盖已有基线 |

脚本里已经有一道拦阻：**Android 不支持专用服务器**（`-Platform Android -Target Server` 会被直接拦掉）。

> 但**验证过的只有 `Win64 + Client`**：chunk 0~8、`-RunChunkAssigner`、PakFileRules 覆写、
> ZenServer 常驻、三条收尾规则，全部只在 Windows 客户端上跑过。

### 11.2 三个目标的差异（这才是要设计的部分）

| | PC 客户端 | 安卓客户端 | 专用服务器 |
| --- | --- | --- | --- |
| 现在能不能打 | ✅ 已验证 | ⚠️ 脚本支持，**没跑过** | ⚠️ 脚本支持，**没跑过** |
| 现有分发方式 | 启动器 → 下载站（chunk 包） | APK + **OBB**（`bPackageDataInsideApk=False`），启动器按版本下整包 | **git**（服务器分区那条线：推仓库、服务器拉、可回退） |
| 分包有没有意义 | 有（就是为它做的） | **要先定**：OBB 是整体更新的，如果继续用 OBB，chunk 划分只是白分 | **大概率没有**（git 本来就是文件级差异） |
| 需要注意 | — | ① IoStore / oplog / PakFileRules 在 Android cook 上是否同样成立，**必须实测**；② `bBuildHttpChunkInstallData=True` 会额外产 `ChunkInstallData`（HTTP chunk 安装用），要么用起来、要么关掉免得混淆 | 服务器 cook 只含服务器需要的资源 → **同一份规则在 Server 下大量 0 命中**，"空规则"体检会变成假警报 |

### 11.3 我倾向的做法（**待你确认**）

1. **服务器不分包**：`-Target Server` 时不生成 PakFileRules、不传 `-RunChunkAssigner`，出一个整体包交给 git 那条线。
   理由：服务器更新走 git（文件级差异比 chunk 细），而且规则里的客户端素材在服务器上本来就是 0 命中。
2. **页面上按"目标"分开**：PC 客户端 / 安卓客户端 / 服务器三个入口（对应你在截图里看到的按平台分类的按钮），
   每个目标**独立的报告**：`Saved\PackLogs\ChunkReports\<平台>-<目标>\...json`；
   体检、体积、变更都按目标分别统计（否则客户端的命中数会污染服务器的判断）。
3. **安卓要走一轮实测**：规则共用是确定的（用户已定 PC/Android 共用一份），
   但"Android cook 上 IoStore + oplog + PakFileRules 是否同样成立"必须真跑一次才知道。
   建议紧接着做一次 `-Platform Android -Target Client -Mode Quick`。
