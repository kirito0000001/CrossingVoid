### 3.3 分包链路排查（做完，结论已定）

详见 `Plugins\DreamChunkDownloader\Docs\2026-09-18-分包链路排查记录.md`。

**核心结论：**

```
官方 chunk 分配 = UAT 的 OplogChunkAssigner（写 ChunkManifest/pakchunkN.txt）
                    ↓ 必须
              读 Zen store 的 oplog（-ProjectId / -OplogId）
                    ↓ 必须
              bUseZenStore=True
                    ↓ 引擎强制要求
              bUseIoStore=True
                    ↓ 后果
              产出 .utoc/.ucas，不是 .pak
```

引擎自己的原话（cook 日志 `LogProjectPackagingSettings`）：

> `bUseZenStore` is enabled in your project packaging settings while `bUseIoStore` is
> disabled. **This is not a supported combination. `bUseZenStore` is being treated as disabled.**

所以日志里的 `ChunkAssignment op not cached on PackageStoreData` 不是我们配错，
而是**这个组合在 5.8 里根本不成立**。这也是 HotChunker 这类插件存在的原因。

> **后来的修正（见第九节）**：上面这条只解释了「为什么默认配置下没有 op」。
> 真正的操作原因是**打包命令少传了 `-RunChunkAssigner`**；把两个开关都打开再补上这个参数，
> 链路是能完整跑通的。所以「链路是死的」这个说法要收回，**准确说法是「链路需要显式开启，
> 而且它的分配规则不是我们想要的」**。

An error occurred while sending the request.

1. **临时**（本次用的）：手动 `Start-Process` 起 `zenserver.exe`（参数照抄引擎启动日志里的那串，

2. **正式**（推荐）：把它装成服务 —— 引擎自带这个功能：
   `zen.exe service install`（同目录还有 `status` / `start` / `stop` / `uninstall`）。

> 本次排查时手动起的那个 ZenServer 进程**还开着**（PID 会变）。不需要的时候直接结束进程即可。

## 九、路线 A 实测结果（2026-09-18 23:03）与下一步

### 9.1 结论：官方链路是通的，但它不认标签

两个开关都置 `True` 之后又跑了两轮，结果如下。

**第一轮（不带 `-RunChunkAssigner`，等同于原来的打包方式）：**

- 产物里**还是没有 pakchunk7**，仍然只有 0/2/3
- 日志里那句 `ChunkAssignment op not cached on PackageStoreData` 依旧存在
- 原因：**UAT 有个命令行开关 `-RunChunkAssigner`，我们的打包命令从来没传过它。**
  不传它，`OplogChunkAssigner` 这一步根本不会执行 → oplog 里没有 ChunkAssignment op
  → pak 步骤退回去读磁盘上那份旧的 `ChunkManifest\pakchunkN.txt`（就是那 3 条）

**第二轮（带上 `-RunChunkAssigner`）：**

第一次因为 ZenServer 已退出而 **BUILD FAILED**（见 8.1.1）。把 ZenServer 常驻之后再跑，**完整跑通**：

```
OplogChunkAssigner starting.
  Using default chunk assigner
  DefaultChunkAssigner: assigning chunks for 11285 packages.
  DefaultChunkAssigner: built 11921 file entries across 11285 packages in 2 chunks.
  OplogWriter: appended op 'ChunkAssignment' (278194 bytes) to CrossingVoid.ba5ac229.Windows
  LogUnrealChunkAssigner: Updated asset registry: ...\CrossingVoid\AssetRegistry.bin
  LogUnrealChunkAssigner: Updated asset registry: ...\Metadata\DevelopmentAssetRegistry.bin
  OplogChunkAssigner complete.
ChunkAssignmentOp: parsed 2 chunk(s) from oplog
  ReadChunkAssignmentOp: chunk (pakchunk0)  has 320 files.
  ReadChunkAssignmentOp: chunk (pakchunk10) has 11593 files.
  Creating pak C:/.../pakchunk0-Windows.pak
  Creating pak C:/.../pakchunk10-Windows.pak
```

**所以：官方 oplog 分包链路本身完全能用，是我方打包命令少了开关。**

**但是它不认我们的标签。** 引擎自带的 `DefaultChunkAssigner` 的规则就两条
（`Oplog\DefaultChunkAssigner.cs` 第 30~45 行）：启动包 → chunk 0，**其余全部 → chunk 10**。
它压根不看 `PrimaryAssetLabel` 的 ChunkId。这就是「只出 0 和 10」的原因。

## 九·补、方案定案（2026-09-18 深夜 · 第二版）：用引擎自带的 PakFileRules

第九节原来的结论是「必须自己写一个 `ChunkAssigner`」。**查完资料 + 跑过一次实验之后，这条推翻了**：
引擎自带一个配置机制 `DefaultPakFileRules.ini`，能做到同样的事，**不用写 C#、不用改引擎**。

### 出处

> 出处：UE5 非uasset资产Chunk/Pak 划分踩坑笔记（<https://zhuanlan.zhihu.com/p/689375430>，作者 飞云）
> 原文要点：「bOverrideChunkManifest=true … 允许覆盖来自 cooker 的分块清单分配」「OverridePaks="pakchunk1"
> … 如果设置，表示要将文件存放入哪个 Pakchunk」「+Files=".../Content/Lua/" 文件夹下所有文件（递归）」
> 我们的验证：见下面的实验结果 —— **成立**。

引擎侧的权威定义（自带的 `Engine\Config\BasePakFileRules.ini` 原文）：

```
; These rules are applied in order, the first rule that applies per file is taken and no others are evaluated
; [SectionName]
; bOverrideChunkManifest=false   ; If true this allows overriding assignments from the cooker
; bExcludeFromPaks=false         ; If true this removes entirely, cannot coexist with overridepaks
; OverridePaks="pakchunk1"       ; If set this will override pak list, comma separated
; Platforms="iOS,Android"        ; If set this rule will only apply to these platforms
; Targets="Shipping,Test"        ; If set this rule will only apply to these configurations
; bOnlyChunkedBuilds=true        ; If set this rule will only apply to chunked builds
; +Files=".../*FileMask*.*"      ; List of file masks to apply to, using the C# FileFilter class
```

读两个文件，工程侧的会叠加在引擎侧之上：
`<引擎>\Config\BasePakFileRules.ini` + `<工程>\Config\DefaultPakFileRules.ini`

### (4) 语义修订：未分类 = 本次新增，要单独成新 chunk（**2026-09-19 凌晨，用户澄清**）

**原来的实现是错的**：之前兜底规则把「未分类资源」收进 **chunk 0（基础包）**。
用户澄清了正确语义：

> 未分类的应该是新建一个 chunk 合集的，也就对应着一次常规补丁的打包，不会落到 0。作为纯新增内容。

也就是说：

- 规则里**已经登记**的目录 = 上次发包就有的内容，chunk 号固定不变；
- 规则里**没登记**的目录 = 这次新加的素材 → **单独成一个新 chunk**（一次常规补丁的载体），
  这样启动器只需要下一个新包，基础包一个字节都不动；
- 所以「未分类」不是异常状态，而是「本次补丁要发的东西」。

**生成器改动（`Tools\Build-PakFileRules.ps1`）**：

| 改动 | 说明 |
| --- | --- |
| 兜底目标默认 = 现有最大 chunk 号 + 1 | `-UnclassifiedChunkId -1`（自动）；显式给数字仍然可用 |
| 匹配掩码带上工程名 | `/Game/X` → `.../<工程名>/Content/X/...`。原来只用 `.../Content/...`，会把引擎自带的 `Engine\Content\...` 也一起卷进来 |
| 兜底拆成两条 | **A** `[CC_NewContent]` 本工程 Content 未分类 → 新 chunk；**B** `[CC_BaseRest]` 其它一切带 Content 的东西（引擎/插件）→ chunk 0 |

兜底 B 为什么必须有：兜底 A 不再扫引擎内容之后，那些引擎依赖会留在默认分配器给的
**chunk 10** 里，变成一个「玩家要额外下载、又不是我们素材」的包。它们属于基础包。
顺序上 B 必须在 A 之后（规则首个匹配生效）。

**插件改动**：未分类的状态行从「打包时落到 Chunk 0（基础包）」改成
「**当前：未分类 —— 本次新增，会进新建的 Chunk N**」（N 实时算 = 现有最大号 + 1，与生成器同算法）。

**已编译 + 已验证**（编辑器已关，`Build.bat CrossingVoidEditor Win64 Development` 通过）：

第一次跑出来的结果里发现一个**必须修的问题**：`pakchunk8` 里除了真素材，还混进了

## 十一、方法论教训（写给下一个会话，都是这次真踩的）

1. **字段对 ≠ 生效。** 这次在这个坑上连错四次，每次都是「先立假设 → 跑一次验证」。
   正确顺序是：**先把源码读穿，再动手**。最后一次按这个做，一次就定位到根因。
2. **不要拿间接证据当结论。**「写入字段的代码是对的」「别人调了同一个 API」都推不出「机制可用」。
3. **不要拿历史产物和新改动做交叉比对。** 这次踩过一次：拿改动前的 csv 比改动后的标签，得出过完全相反的结论。
4. **先查资料再验证**（用 `$zhihu` 技能）：这次从知乎和 HotPatcher 文档各拿到关键线索，
   其中「Priority 打包时失效」直接推翻了一个设计方向。
5. **不同作者可能给出相反结论**（Priority 就是例子）——遇到矛盾不要选边，只能自己验。
