# 零境交错 打包说明

## 怎么跑

```powershell
cd C:\CrossingVoid\Tools

# ① 快速验证：确认 chunk 打包生效（最快，先跑这个）
.\Pack-CrossingVoid.ps1 -Mode Quick

# ② 建基线：正式发布用，只做一次
.\Pack-CrossingVoid.ps1 -Mode Base -ReleaseVersion 1.0

# ③ 打补丁：改完内容后，产 _P.pak
.\Pack-CrossingVoid.ps1 -Mode Patch -ReleaseVersion 1.0
```

如果提示「禁止运行脚本」，先执行一次：

```powershell
Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass
```

（`-Scope Process` 只对当前窗口生效，关掉就恢复，不改系统设置）

## 三种模式的区别

页面上按"平时最常用"排：

| 顺序 | 模式 | 做什么 | 什么时候用 |
| --- | --- | --- | --- |
| 1 | **常规补丁更新**（Patch） | 基于基线算差异，产 `_P.pak` | 基线建好之后，每次改内容 |
| 2 | **版本更新**（Base） | 完整链路 + 建基线 | 一个新基线版本的第一次发布 |
| 3 | **快速验证**（Quick） | cook + stage + pak，**不建基线** | 只想看 chunk 生不生效 |

**Quick 和《版本更新》只差一件事：建不建基线**，其余完全一样。

`-stage` 三个模式都必须有 —— pak 是从 staging 目录生成的。
`-build` 在 Shipping 目标缺失时自动补上（第一次打包必然如此）。

### 「忽略缓存全量重 cook」现在是自动判断

以前菜单里有「版本更新（完全重新编译）」，得自己判断这次该用哪个。现在合并成一项，脚本在《版本更新》时自动体检：

- 扫 `Saved\Cooked\<平台>\<工程>\Content`，看有没有**工程里已经不存在的资产**（上次 cook 之后被删掉或改名的残留）
- **有** → 自动加 `-clean` 全量重 cook（约 43 分钟），日志里列出前 8 个过期文件
- **没有** → 照走增量，省时间
- 想手动强制全量：命令行加 `-Cook`

《常规补丁》**永远不参与这个判断** —— 补丁要跟基线用同一份 cook 数据，重 cook 会让差异算错。

## 产物在哪

```
D:\Build\CrossingVoid\Windows\CrossingVoid\Content\Paks\
```

看什么：
- `pakchunk0-Windows.pak` ~ `pakchunkN-Windows.pak` → **chunk 生效了**
- `pakchunkN-Windows_P.pak` → **补丁包产出来了**（Patch 模式才有）

脚本跑完会自动列出这些 pak 和各自大小，另存一份清单到 `Saved\PackLogs\`。

同级目录 `D:\Build\CrossingVoid\Windows\` 下还有 UAT 产的 stage 清单，
都是纯文本，比 pak 好读：

| 文件 | 内容 |
| --- | --- |
| `Manifest_UFSFiles_Win64.txt` | 所有进 pak 的资产（零境约 24965 条） |
| `Manifest_NonUFSFiles_Win64.txt` | 散文件（mp4 等不进 pak 的） |
| `Manifest_DebugFiles_Win64.txt` | 调试文件（`.pdb` 会被归到这里；我们默认不产 pdb，见文末「pdb 与符号文件」） |

## 查看某个 pak 里到底装了什么

UE 自带的 `UnrealPak` 可以直接列 pak 内容：

```powershell
D:\UnrealEngine-5.8.2\Engine\Binaries\Win64\UnrealPak.exe `
  "D:\Build\CrossingVoid\Windows\CrossingVoid\Content\Paks\pakchunk2-Windows.pak" -List
```

输出里两行最关键：
- `mount point "..."` —— 这个 chunk 对应哪个资源目录
- `N files (M bytes)` —— 实际装了几个文件

**排查 chunk 划分对不对，就用这个命令。**
如果 mount point 指向的目录实际有 28 个资产，但 pak 里只有 2 个，
说明 label 没圈住 —— 见下面「chunk 划分」一节。

## chunk 划分的坑：label 圈的是「引用可达集」

用 `PrimaryAssetLabel` 分 chunk 时有个经典陷阱：

**它圈的是「从 label 出发沿引用能到达的资产」，不是「某个目录下的所有文件」。**

所以会出现这种情况：

```
Cultivate_Image/ 目录实际有 28 个资产
  → 只有 Cultivate_Settle_1、_2 进了 chunk2（因为它们被别处引用了）
  → 其余 26 个没人引用 → 被当成"无主资产" → 全塞进 pakchunk0
```

**后果**：`pakchunk0` 越滚越大（零境占 99.8%），热更新粒度退化成"整个包"。
改一个贴图 → 重下 1.6 GB。

**判断方法**：用上面的 `UnrealPak -List`，对比 mount point 目录的资产数
和 pak 里的实际文件数。差得多就是没圈住。

## 容易踩的坑（都是实测撞过的）

**坑 1：`-manifests` 不能省。**
`DefaultGame.ini` 里的 `bGenerateChunks=True` 只是「允许」产 chunk，
真正让 cook 阶段产 chunk 清单的是命令行上的 `-manifests`。
少了它，就算 ini 里开着，也只出一个大 pak，不分块。

**坑 2：UE 5.8 没有 `-nochunks` 这个参数。**
在 5.3 左右的旧版本里它存在，5.8 源码里已经删了。
所以「之前关掉过 chunk」的那个开关，在新版里已经不存在了 ——
现在控制它的只有 `-manifests` 给不给。

**坑 3：`-stage` 不能省。**
pak 是从 staging 目录生成的。少了 `-stage`，UAT 会直接报：

```
Only staged builds can be paked, use -stage or -skipstage.
AutomationTool exiting with ExitCode=1 (Error_Unknown)
```

（这个坑真踩过，Quick 模式第一版就是这么挂的）

**坑 4：第一次打 Shipping 包必须编译 C++。**
编辑器只产出 Editor 目标（`CrossingVoidEditor.target`），
打包要的是 Shipping 目标（`CrossingVoid-Win64-Shipping.target`）—— 两个不同的东西。
缺了它会报：

```
Stage Failed. Missing receipt 'C:\CrossingVoid\Binaries\Win64\CrossingVoid-Win64-Shipping.target'.
Check that this target has been built.
AutomationTool exiting with ExitCode=103 (Error_MissingExecutable)
```

脚本会自动检测 Shipping 目标是否存在，**不存在就自动补上 `-build`**，不用你手动管。

⚠️ 另外：`-build` 和 `-nocompile` 不能同时给 —— 会打架，Shipping 目标永远产不出来。
脚本已经处理成互斥。

**坑 5：cook 很慢，但缓存能复用。**
零境全量 cook 实测约 **43 分钟**（2584 秒）。
cook 产物缓存在 `Saved\Cooked\Windows\`，后续打包会增量复用，不会重跑一遍。
只有加 `-Cook`（全量重 cook）才会从头再来。

**cook 慢是正常的**，不是卡死。耐心等，或者去干点别的。

**坑 6：第一次编 Shipping 要重编整套引擎，约 75 分钟。**
编辑器只编过 Development 版引擎模块，打 Shipping 包要把引擎重编一遍。
实测 863 个编译单元、**4527 秒（约 75 分钟）**。这是一次性开销。

**坑 7：编译期间日志不动，不代表卡死。**
UBA（Unreal Build Accelerator）把编译进度写进**它自己的日志**：

```
D:\UnrealEngine-5.8.2\Engine\Programs\AutomationTool\Saved\Logs\UBA-<Target>-<平台>-<配置>.txt
```

里面有真实的 `[N/863] Compile [x64] Module.XXX.cpp` 进度。

**我们脚本记的 `Saved\PackLogs\pack-*.log` 在编译期间不更新** —— 那是正常的。
想确认有没有在跑，看这两个：

```powershell
# ① dotnet 进程（UBT 是 .NET 程序，名字就叫 dotnet）
(Get-Process -Name dotnet -ErrorAction SilentlyContinue).CPU

# ② UBA 日志的更新时间
Get-Item "D:\UnrealEngine-5.8.2\Engine\Programs\AutomationTool\Saved\Logs\UBA-*.txt" |
  Sort-Object LastWriteTime -Descending | Select-Object -First 1 Name, LastWriteTime
```

**别用 `Get-Process *Unreal*` 找编译进程** —— 找不到的，UBT 叫 `dotnet`。

## 参数备忘

| 参数 | 作用 |
| --- | --- |
| `-cook` | 烘焙资产（**很慢，零境约 43 分钟**） |
| `-manifests` | **产 chunk 清单（chunk 分块的真正开关）** |
| `-build` | 编译 C++（产 Shipping 目标，第一次必跑） |
| `-stage` | 组装产物目录（**pak 的前提**） |
| `-pak` | 打成 pak |
| `-compressed` | 用 ini 里的 Oodle/Kraken 压缩 |
| `-archive` | 输出到归档目录（不加就只在 StagedBuilds） |
| `-archivedirectory=<路径>` | 归档根目录 |
| `-createreleaseversion=<版本>` | 建基线，供 patch 用 |
| `-generatepatch` | 产 `_P.pak` |
| `-basedonreleaseversion=<版本>` | 基于哪个基线算差异（**必须配 generatepatch**） |
| `-nocompile` | 跳过编译检查（**不能和 `-build` 同时给**） |
| `-clean` | 全量重 cook，必须紧跟 `-cook` 后面 |
| `-Cook` | （脚本自己的开关）**强制**全量重 cook；平时由缓存体检自动决定 |
| `-ClearCache` | 只清能再生的缓存然后退出（不打包），页面上的《清除缓存》按钮走这条 |
| `-DryRun` | 只列不删（配 `-ClearCache` 用）/ 只打印命令行 |

## 清缓存（腾磁盘）

页面《二游打包》右上角有个 **《清除缓存》** 按钮，命令行是同一条：

```powershell
.\Pack-CrossingVoid.ps1 -ClearCache

# 只想看会清掉多少、不动手
.\Pack-CrossingVoid.ps1 -ClearCache -DryRun
```

只删这三样（都能自动重建）：

| 目录 | 是什么 | 删了之后 |
| --- | --- | --- |
| `Saved\StagedBuilds` | UAT 组装的产物 | 下次打包重新组装 |
| `Saved\Cooked` | cooked 数据 | 下次 cook 从头来（慢一些） |
| `Saved\Shaders` | shader 缓存 | 下次重新编译 shader |

**不碰**：`Intermediate\Build`（编译中间物，重编很贵）、`Content`、归档目录、`Releases` 基线。
脚本里还有一层兜底：删之前解析真实路径，不在工程内的直接拒绝。

## 基线存在哪

```
D:\DabaoV\Crossingvoid\Release\<基线版本>\<平台>\
```

比如 `D:\DabaoV\Crossingvoid\Release\0.5\Windows\`（客户端）。

基线里装的是**那一次打出来的 pak 容器本体**（`.pak` + `.sig` + IoStore 的 `.utoc`/`.ucas`），
大小 ≈ 那次所有 chunk 容器之和（客户端约 1.5 GB）。UAT 源码原话：
`copy the created pak to the release version directory we might need this later if we want to generate patches`

**刻意放在 D 盘**——C 盘是系统盘，而一条基线 1.5 GB。根目录只在脚本的 `$ReleaseRoot`
常量里定义一次，同时传给 UAT 的两个参数：`-createreleaseversionroot`（写）和
`-basedonreleaseversionroot`（读），两者必须同根。

**这个目录别乱删** —— 删了以后所有基于它的 patch 都算不出差异。
脚本在建基线前会检查它是否已存在，存在就报错拦下来。

## 两个"版本号"不是一回事

|  | 玩家版本 | 基线版本 |
| --- | --- | --- |
| 给谁看 | 玩家（APK 应用信息里显示的那个） | 只有打包流程 |
| 存在哪 | `Config\DefaultEngine.ini` → `AndroidRuntimeSettings.VersionDisplayName` | `D:\DabaoV\Crossingvoid\Release\<号>\` 这个目录名 |
| 什么时候改 | 每次发版想改就改 | 每次《版本更新》换一个新号 |
| 页面上的取值 | 你填 | **由玩家版本自动推出来，只读不能改**：`0.5.13` → `0.5` |

`StoreVersion`（versionCode）刻意保持 1 不动。一条基线覆盖它下面所有小版本的补丁：
玩家版本 `1.4.2` / `1.4.5` 都基于基线版本 `1.4`，不用每次重建基线。

## pdb 与符号文件（为什么产物里没有 pdb）

**结论：Windows 的 Shipping 包本来一定会产 pdb；要关掉必须两个开关一起给
（`-NoDebugInfo` + `-NoLinkerDebugInfo`），缺一个都不行。**

| 产物 | pdb | 大小 |
| --- | --- | --- |
| 客户端 | `CrossingVoid-Win64-Shipping.pdb` | 约 1.6 GB |
| 服务器 | `CrossingVoidServer-Win64-Shipping.pdb` | 约 1.5 GB |

它们本来会跟着归档目录一起走 —— UAT 把它们归到 `StagedFileType.DebugNonUFS`，
也就是上面提到的 `Manifest_DebugFiles_Win64.txt`。

### 为什么"不想要"还得专门关两刀

引擎在 Windows 上是**两段式**，只看一段会得出错误结论（我们就是这样先错了一次）：

**① 编译期**——`UEBuildPlatform.cs:1367-1369`

```csharp
GlobalCompileEnvironment.bCreateDebugInfo =
    Target.DebugInfo != DebugInfoMode.None && ShouldCreateDebugInfo(Target);
GlobalLinkEnvironment.bCreateDebugInfo = GlobalCompileEnvironment.bCreateDebugInfo;
```

关键：`ShouldCreateDebugInfo(Shipping)` 返回 `!bOmitPCDebugInfoInDevelopment`，
而那个开关**默认是 false**（而且只有 `[XmlConfigFile]`，命令行给不了）
→ **Shipping 的编译期调试信息默认是开的** → 链接期一开始就抄到 `true`。

**② 链接期**——`UEBuildWindows.cs:2175-2184`：

> 原文："NOTE: Even when debug info is turned off, we currently force the linker to generate debug info anyway on Visual C++ platforms. This will cause a PDB file to be generated with symbols for most of the classes and function/method names, so that crashes still yield somewhat useful call stacks..."
>
> ```csharp
> if (!Target.WindowsPlatform.bNoLinkerDebugInfo)
> {
>     GlobalLinkEnvironment.bCreateDebugInfo = true;
> }
> ```

这句是**"不再强制打开"**，不是"关掉"——它管不了 ① 已经打开的 `true`。

**所以：**

| 给什么 | 编译期 | 链接期 | pdb |
| --- | --- | --- | --- |
| 什么都不给 | true | true | **有** |
| 只给 `-NoLinkerDebugInfo` | true | true（抄来的） | **还是有** ← 我们踩过的坑 |
| 只给 `-NoDebugInfo` | false | true（被 ② 强制打开） | **还是有** |
| 两个都给 | false | false | **没有** ✓ |

> 实测：2026-09-19 14:26 那次服务器打包只带了 `-NoLinkerDebugInfo`，
> 结果 `CrossingVoidServer-Win64-Shipping.pdb` 照样产出了 1544.6 MB。

### 这个开关的完整链路（在 5.8 源码里逐环验证过，不是猜的）

| 环节 | 源码位置 | 说明 |
| --- | --- | --- |
| 开关本体 | `Platform\Windows\UEBuildWindows.cs:698-703` | `[XmlConfigFile(Category="WindowsPlatform")]` + `[CommandLine("-NoLinkerDebugInfo")]`，默认 false |
| 命令行怎么进去 | `Configuration\Descriptors\TargetDescriptor.cs:380` → `Configuration\Rules\TargetRules.cs:3362-3367` | 目标描述符携带整条命令行，之后 `Arguments.ApplyTo(WindowsPlatform)` |
| 能不能写 ini | **不能** | 该字段只有 `[XmlConfigFile]`（对应 BuildConfiguration.xml），没有 `[ConfigFile]`，写进 `DefaultEngine.ini` 无效 |
| 链接器侧 | `Platform\Windows\VCToolChain.cs:1738-1749, 3493-3510` | 只有 `bCreateDebugInfo` 为真才加 `/DEBUG:FULL` 和 `/PDB:` |
| 归档时会不会报错 | `AutomationUtils\DeploymentContext.cs:1029-1035` | 注释原文 "Symbol files aren't true dependencies so we can skip if they don't exist" —— 没有 pdb 就静默跳过 |

### 我们脚本的做法

`Pack-CrossingVoid.ps1` 默认给 Windows 的 Shipping 目标加**两个**开关：

- 独立编译那一步：`Build.bat <目标> Win64 Shipping -Project=... -WaitMutex -NoDebugInfo -NoLinkerDebugInfo`
- **代价**：`-NoDebugInfo` 改了编译参数 → 该目标要**全量重编一次**（编完中间物也会变小）
- **只在这一步加**，不给 UAT 传 `-ubtargs`：`-ForceBuild` 时 UAT 那一轮
  （编辑器目标也在一起）是整轮生效的，会把 Rider 调试用的编辑器 pdb 一起干掉
- 归档之后仍然兜底扫一遍 `*.pdb` 再删（防的是「复用旧 exe / 旧 pdb」——
  打包默认 `-nocompile`，本来就不会重新链接）

想保留 pdb 就加 `-KeepSymbols`：那时不加这个参数，归档也保留。

### 唯一的副作用

关掉之后链接器不再产任何调试信息，于是：

- 崩溃栈只有「模块名 + 偏移」，没有函数名和行号。
- 本地 `C:\CrossingVoid\Binaries\Win64\` 里现在那两个老 pdb（1.6 GB + 1.5 GB）是
  **上一次构建**留下的，跟以后编出来的 exe 对不上，留着也没用；确认不需要就删掉，省 3.2 GB。
- 以后若想能符号化服务器崩溃：用 `-KeepSymbols` 打包，并且那份 pdb **只留本地**（别进包、别进 git）。

> 出处：知乎《UE4/5 客户端崩溃分析》（https://zhuanlan.zhihu.com/p/1891179882790253014）
> 原文摘要："打包时提示缺少PDBCOPY.EXE无法剥离符号，是因为Windows SDK组件缺失了Windows Debugging Tools，安装对应组件即可正常完成符号剥离，大幅压缩安装包体积。对于已经打包完成的版本，手动删除对应输出目录中的 `.p[db]`"
> 我们的验证：引擎源码 `Automation\Win\WinPlatform.Automation.cs:670-677` 确实在找不到 `pdbcopy.exe` 时直接抛 `AutomationException` —— 证实「剥离符号」这条路依赖 Windows Debugging Tools。所以我们不走剥离、也不事后手删，而是从源头不生成（顺带省掉 1.5 GB 的写盘和链接时间）。
> 中文社区里的常见做法只有三种：剥离、手动删、换 Development 少产符号；`bNoLinkerDebugInfo` 这个开关在知乎站内搜索里 0 条命中，是读 5.8 源码得到的。
