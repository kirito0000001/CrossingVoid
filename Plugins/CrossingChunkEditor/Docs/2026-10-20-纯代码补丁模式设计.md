# 纯代码补丁模式（Code-Only Patch）设计与调研

> 记录于 2026-10-20。状态：**阶段 A 曾以脚本 `-CodeOnly` + 面板「代码补丁」按钮实现；
> 2026-10-27 起按钮和这两个参数都已删除**，统一并进《常规补丁》的变化扫描（见 README 5.1）。
> 阶段 B（模块化原型）与阶段 C（正式切模块化）未做。
> 本文是历史设计与调研记录，实际行为以 README 为准。
> **2026-10-20 修订（架构优先）**：推荐方案从“全量 exe 替换”改为
> **客户端模块化 Shipping + BuildId 回收 + 运行时二进制镜像**。
> 全量 exe 降级为回退方案；二进制 delta 与脚本层作为后续/补充层。
>
> 目标：只改了 C++ 逻辑时，不跑 cook/pak，尽量只下发变化的游戏模块 DLL；
> 引擎/内容不动时，玩家不需要重下整个 152 MB 的 Shipping exe。

---

## 0. 结论先行

1. **C++ 逻辑编进 exe/DLL，不进 pak/chunk。** `_P.pak` 只能带 cooked 资产；代码补丁不是“打 pak”。
2. 当前客户端/服务器都是 **monolithic Shipping**：归档里只有一个大的 `*-Win64-Shipping.exe`，没有 `.modules`、没有游戏 DLL。
3. 启动器是**文件级清单**（`files[]` = path/size/sha256），更新时只下 sha256 变的文件；`patches[]` 恒空，UE `_P.pak` 暂缓不用。
4. **目标架构（长期）**：
   - **客户端**：`LinkType = Modular`，引擎 DLL 与游戏模块 DLL 分离；
     只改游戏代码时，UBT 会**回收 BuildId**，只更新变化的游戏 DLL（+ 必要时 `.modules` / `.version`），引擎 DLL 不动。
   - **服务器**：保持 **Monolithic + Unique**。服务器是散件/git，带宽不是玩家问题；
     而且 `bUseLoggingInShipping` / `bUseConsoleInShipping` 要求 `Unique`（UBT `TargetRules.cs:1608-1617`），改 Shared 会牵动这两个开关。
   - **插件侧**：代码补丁模式不做“只替换一个 exe”的硬编码，而是做**运行时二进制镜像**——
     对比构建输出与归档里的 `Binaries`，只覆盖变化的 `.exe/.dll/.modules/.version`。
     这样今天 monolithic 能用，将来切 modular 不用重写。
5. **必须先做模块化原型再拍板**：UBT 源码支持 BuildId 回收，但实际是否按预期回收、
   启动/内存/插件兼容性如何，必须用一次真实 modular Shipping 构建 + 一次“只改 .cpp”的二次构建来验证。
   验证不通过就回退到 **monolithic + 二进制 delta**，或者把高频逻辑迁到脚本层。
6. **安全边界**：只改 `.cpp` 函数体最安全；动了头文件里的
   `UPROPERTY/UFUNCTION/UCLASS/USTRUCT/UENUM`、自定义序列化、Shader、资产或配置，必须走完整 cook。

---

## 0.1 路线图（一句话版）

> **客户端模块化 → 先用一次实验验证 → 通过就切、没通过就回退 delta；服务器不动；
> 插件先做成布局无关的二进制镜像。**

| 阶段 | 做什么 | 产出/决策 | 谁来做 |
|---|---|---|---|
| **A. 插件二进制镜像（先做）** | 加「代码补丁（仅编译）」：只 build Shipping，对比构建输出与归档，只覆盖变化的运行时二进制 | 今天 monolithic 可用（镜像 exe）；将来 modular 自动镜像 DLL；含变化扫描/报告/按钮 | 我改插件，你编译 |
| **B. 模块化实验（一次）** | 客户端 Game target 临时改 `LinkType=Modular`，全量构建一次；只改一个 `.cpp` 再构建一次 | 看三件事：BuildId 是否复用、是否只有游戏 DLL 变、启动/插件是否正常 | 我准备 target/命令，你跑构建 |
| **C. 正式切模块化（如果 B 通过）** | 客户端正式 Modular，重打一次完整包（新版本/新碎片）；服务器保持 Monolithic/Unique | 以后代码补丁只下游戏 DLL；引擎 DLL 不动 | 我改 target/脚本，你发一次完整包 |
| **D. 回退/补充（如果 B 不通过）** | 保持 Monolithic；启动器加二进制 delta（`patches[]`）；或高频逻辑迁脚本层 | 代码补丁仍可用，只是下载量大一些 | 后续再定 |

**决策规则**：不看感觉，看 B 的三个结果。
- BuildId 复用 + 只有游戏 DLL 变 + 启动/插件正常 → 走 C。
- 任何一项不成立 → 走 D（Monolithic + delta），不要在模块化上硬耗。

**服务器为什么不一起模块化**：`bUseLoggingInShipping` / `bUseConsoleInShipping` 要求 `Unique`（`TargetRules.cs:1608-1617`）。服务器要日志/控制台，且走 git 散件，不需要小补丁；保持 Monolithic/Unique 最稳。

## 1. 本机产物核对（不是推测）

### 1.1 归档实际结构

| 项 | 客户端 | 服务器 |
|---|---|---|
| 归档根 | `F:\DaBaoV\Fantasy\Windows` | `F:\DaBaoV\Fantasy\WindowsServer` |

| 游戏 exe | `FantasyProject\Binaries\Win64\FantasyProject-Win64-Shipping.exe`（152,519,680 B） | `FantasyProject\Binaries\Win64\FantasyProjectServer-Win64-Shipping.exe`（143,427,584 B） |
| `.modules` | **无** | **无** |
| 游戏 DLL | 无（同级只有 `tbb12.dll` / `tbbmalloc.dll`） | 同上 |

关键发现：

- **归档子目录名是工程名**（`FantasyProject`），不是 target 名。服务器 exe 叫 `FantasyProjectServer-...`，但仍在 `WindowsServer\FantasyProject\Binaries\Win64\` 下。
- `F:\DaBaoV\Fantasy\Windows\FantasyProject\Binaries\Win64\FantasyProject-Win64-Shipping.exe` 与工程构建输出 `D:\UnrealMap\FantasyProject\Binaries\Win64\FantasyProject-Win64-Shipping.exe` 的 SHA256 完全一致（`0b5b7741...`），且是硬链接（link count 2）。
- 启动器 `src/platform/gameCatalog.ts:175` 启动的是根目录 `FantasyProject.exe`，进程名同时监听 `FantasyProject.exe` / `FantasyProject-Win64-Shipping.exe`。代码补丁**不需要动根 shim**。
- 归档是 monolithic：没有 `.modules`，没有游戏模块 DLL。

### 1.2 为什么当前是 monolithic

UBT 的默认链接方式（`Engine/Source/Programs/UnrealBuildTool/Configuration/Rules/TargetRules.cs:2686-2690`）：

```csharp
get => (LinkTypePrivate != TargetLinkType.Default)
    ? LinkTypePrivate
    : ((Type == TargetType.Editor) ? TargetLinkType.Modular : TargetLinkType.Monolithic);
```

- Editor → Modular；其它（Game/Client/Server）→ **Monolithic**。
- 你们的 `FantasyProject.Target.cs` / `FantasyProjectServer.Target.cs` 都没有设置 `LinkType`，所以是 Monolithic。
- `BuildEnvironment` 默认（`TargetRules.cs:2843-2869`）：源码引擎 + Monolithic → **Unique**；Modular → **Shared**（除非显式覆盖）。

### 1.3 当前工程的 cook 前提（重要）

`D:\UnrealMap\FantasyProject\Config\DefaultGame.ini:10` 实际是：

```ini
bUseIoStore=False
bGenerateChunks=True
```

UE 5.8 的新增量 cook 默认开启，但前提是 **ZenStore 存 cook 结果 + IoStore staging**。
`bUseIoStore=False` 时这个前提不满足，可能退回 LegacyIterative 或完整 cook。
**纯代码补丁跳过 cook，等于绕过这层安全检查**——这是下面“安全边界”要单独讲的原因。

## 2. 代码 vs 资产的边界（多来源一致）

| 结论 | 来源 |
|---|---|
| C++ / `.cpp` 改动不能用 pak 热更；补丁只能覆盖 `.uasset`，C++ 必须重新编译 + 重打包 | Banming《UE 热更》原文：“坑 8：C++ / .cpp 改动无法用 pak 热更。补丁只能覆盖资产（.uasset）。C++ 代码改动（.cpp/.h）不在 pak 覆盖范围，必须重新编译 + 重打包。” |
| C++ 是编译型语言，所有变动都要编译，所以 C++ 无法热更；BluePrint 是资产，可以热更 | imzlp《UE热更新：需求分析与方案设计》：“C++ 是个编译型语言，所有的变动都需要执行编译操作，所以 C++ 的代码无法热更。而蓝图本质上是资产（uasset）……” |
| HotPatcher 只做资产/Pak/IoStore 热更，不涉及 exe/DLL | HotPatcher README + 对其功能范围的核对 |
| 另一个“C++ hot-update”仓库 `977908569/GameUpdate` 实际也只挂载 Pak/IoStore 容器，不含 exe/DLL | 该仓库 README 的功能核对：manifest 只有 `utoc/ucas/pak`，无代码加载/替换步骤 |
| `.modules` 是“含 DLL 的输出目录”的 BuildID 清单；二进制发布必须 exe + 所有 DLL + `.modules` 一起 | Epic 官方《Versioning of Binaries》：“every output directory that contains at least one compiled DLL receives a JSON file with the `.modules` extension… you must check in the executable, all DLLs, and their associated `.modules` files together” |
| `_P.pak` 的命名和生成 | `AutomationTool/Scripts/CopyBuildToStagingDirectory.Automation.cs:3868-3876`：`GetPakFilePostFix` 在 `bShouldGeneratePatch` 时返回 `_P` |

**推论**：纯代码补丁不需要 `Patch` 模式的 `-generatepatch`；它生成的是内容 `_P.pak`，不是代码。你们的启动器也不消费 `_P.pak`。

## 3. 架构路线对比

| 路线 | 代码补丁载荷 | 优点 | 代价/风险 | 定位 |
|---|---|---|---|---|
| **A. 客户端 Modular Shipping + BuildId 回收** | 变化的游戏模块 DLL + 必要时 `.modules` / `.version` | UE 原生；游戏代码改动只下小 DLL；引擎 DLL 不动；启动器文件级清单直接适配 | 一次性全量重建；文件数/启动开销略增；插件兼容性要测；BuildId 回收必须实测；服务器日志开关要求 Unique | **目标核心（客户端）** |
| **B. Monolithic + 全量 exe** | 整个 Shipping exe（当前约 152 MB） | 不改运行时结构；实现最简单；任何 C++ 改动都能覆盖 | 每次下 152 MB；引擎/游戏一起重链 | **回退方案** |
| **C. 二进制 delta（`patches[]`）** | exe/DLL/pak 的二进制 diff | 不改构建架构；对引擎更新/大文件也有效；补丁可能几 MB | 启动器要加 patcher、校验、回滚；签名/杀软/PE 兼容性；跨仓库工作量 | **交付层优化**（可与 A/B 叠加） |
| **D. 脚本层（UnLua/Puerts/Angelscript）** | 脚本资产（pak/文件） | 逻辑真热更；Windows/Android 都能用；无需二进制 | 需要重写逻辑/暴露 C++ API；VM 性能/调试/团队工作流；C++ 核心仍需二进制 | **高频逻辑的战略选项** |

> **不要**把 `_P.pak` 当代码补丁；它只带 cooked 资产。
> **不要**为了“省事”直接选 B；B 只适合作为模块化原型失败后的回退。

## 4. 模块化代码补丁的关键：BuildId 回收

这是“只更新游戏 DLL”能不能成立的核心。UE 5.8 的 UBT 源码已经写清楚。

### 4.1 UBT 怎么决定 BuildId

`UnrealBuildTool/Modes/WriteMetadataMode.cs:101-118`：

```csharp
if (TargetInfo.Version != null && !String.IsNullOrEmpty(TargetInfo.Version.BuildId))
    BuildId = TargetInfo.Version.BuildId;
else if (TargetInfo.Receipt != null && !String.IsNullOrEmpty(TargetInfo.Receipt.Version.BuildId))
    BuildId = TargetInfo.Receipt.Version.BuildId;
else if (TargetInfo.VersionFile != null
      && BuildVersion.TryRead(TargetInfo.VersionFile, out BuildVersion? PrevVersion)
      && CanRecycleBuildId(PrevVersion.BuildId, TargetInfo.FileToManifest, Logger))
    BuildId = PrevVersion.BuildId;
else
    BuildId = Guid.NewGuid().ToString();
```

### 4.2 回收条件：只看引擎目录

`WriteMetadataMode.cs:247-265`：

```csharp
private static bool CanRecycleBuildId(string? BuildId, Dictionary<FileReference, ModuleManifest> FileToManifest, ILogger Logger)
{
    foreach (FileReference ManifestFileName in FileToManifest.Keys)
    {
        ModuleManifest? Manifest;
        if (ManifestFileName.IsUnderDirectory(Unreal.EngineDirectory)
            && TryReadManifest(ManifestFileName, Logger, out Manifest)
            && Manifest.BuildId == BuildId)
        {
            DateTime ManifestTime = FileReference.GetLastWriteTimeUtc(ManifestFileName);
            foreach (string FileName in Manifest.ModuleNameToFileName.Values)
            {
                FileInfo ModuleInfo = new FileInfo(FileReference.Combine(ManifestFileName.Directory, FileName).FullName);
                if (!ModuleInfo.Exists || ModuleInfo.LastWriteTimeUtc > ManifestTime)
                    return false;
            }
        }
    }
    return true;
}
```

关键点：

- 只检查 **Engine 目录下**的 `.modules`；**Project 目录下的 manifest 不参与判断**。
- 只要引擎 DLL 没有比引擎 manifest 更新，就回收上一版 BuildId。
- 因此：**只改游戏代码（Project/Source 或 Project/Plugins）→ BuildId 不变 → 引擎 DLL 仍然是同一批 → 只更新变化的游戏 DLL 即可。**
- 如果改了引擎代码/引擎 DLL 被重编 → 引擎 manifest 对不上/时间更新 → 生成新 GUID → **所有引擎 + 游戏 DLL 都要更新**（这不是小补丁，应该走完整二进制更新）。

### 4.3 模块化的文件名/布局（源码依据）

| 项 | 规则 | 源码 |
|---|---|---|
| App 名 | Modular + Shared 时，Game → `UnrealGame`，Server → `UnrealServer` | `UEBuildTarget.cs:1912-1921` |
| `.modules` | `UnrealGame-Win64-Shipping.modules`（Shipping 带平台/配置） | `ModuleManifest.cs:72-88` |
| 模块 DLL | `UnrealGame-<Module>-Win64-Shipping.dll` | `UEBuildTarget.cs:5397` |
| `.version` | `UnrealGame-Win64-Shipping.version`（BuildId 也写在这里） | `UEBuildTarget.cs:3285-3293`、`BuildVersion.cs:114-131` |

所以模块化客户端的补丁载荷大致是：

```text
FantasyProject/Binaries/Win64/UnrealGame-FantasyProject-Win64-Shipping.dll   ← 变化的游戏模块
FantasyProject/Binaries/Win64/UnrealGame-Win64-Shipping.modules              ← 模块表/BuildId（可能不变）
FantasyProject/Binaries/Win64/UnrealGame-Win64-Shipping.version              ← BuildId/版本（可能不变）
Engine/Binaries/Win64/...                                                    ← 引擎 DLL，通常不动
```

### 4.4 必须注意的两个边界

1. **服务器不要轻易改 Modular/Shared。**
   `bUseLoggingInShipping` / `bUseConsoleInShipping` 带 `[RequiresUniqueBuildEnvironment]`（`TargetRules.cs:1608-1617`）。
   服务器要日志/控制台就得 `Unique`；保持 Monolithic/Unique、走 git 散件更新更稳。
2. **模块增删/改名 = 结构变更，不要走小补丁。**
   `MergeManifests` 在 BuildId 回收时会把旧 manifest 里、新构建没有的模块**补回去**（`WriteMetadataMode.cs:300-309`）。
   如果删了/改名了一个游戏模块，回收后的 `.modules` 可能还列着旧 DLL → 启动时加载到旧模块。
   所以：改 `.Build.cs` / `.Target.cs` / `.uplugin` / 模块目录结构时，必须**清掉旧的 `.version`/`.modules`，重新生成 BuildId，走完整二进制更新**，不能走纯代码补丁。

### 4.5 生产案例

- Satisfactory 使用 Modular Shipping 发布，并允许加载 `Plugins/` 里的 DLL；Coffee Stain 的反馈是：
  **可执行文件变小、DLL 变多；启动时间和内存“略微增加”，但“really insignificant”**；代码总大小会增加。
  <https://forums.unrealengine.com/t/packageodinplugin-definition/1197488/2>
- 这说明 Modular Shipping 不是理论方案，但有启动/体积代价，必须实测。

### 4.6 原型验证（拍板前必做）

源码逻辑支持回收，但必须用真实构建验证：

1. 分支/副本，给**客户端 Game target**加 `LinkType = TargetLinkType.Modular;`；服务器 target 不动。
2. 全量构建 Shipping，记录：
   - 首次构建时间；
   - 归档文件数/总大小；
   - 启动时间/内存（对比 monolithic）；
   - `UnrealGame-Win64-Shipping.modules` 的 `BuildId`；
   - 游戏模块 DLL 的大小（`UnrealGame-FantasyProject-Win64-Shipping.dll`）。
3. 只改一个 `.cpp`，再构建一次，记录：
   - `.version` / `.modules` 的 `BuildId` 是否与第一次相同；
   - 变化的文件是否只有游戏模块 DLL（+ 可能的 `.modules`）；
   - 引擎 `Engine/Binaries/Win64` 下的 DLL 是否没变；
   - 启动/跑一局是否正常。
4. 测所有运行时插件（DreamChunkDownloader、DreamGameplayTask 等）是否能在 Modular Shipping 下加载。
5. 如果 BuildId 没回收、或启动/插件有问题 → 回退 B 或 C。

> 这一步是“架构决策”的数据来源，不是可选项。没有这组数据，不能拍板模块化。

## 5. 插件侧：运行时二进制镜像（兼容 monolithic / modular）

### 5.1 设计原则

不要写死“替换某个 exe”。代码补丁模式应该做**二进制镜像**：

- **源**：构建输出的运行时二进制
  - `<ProjectRoot>\Binaries\Win64\`
  - `<EngineRoot>\Engine\Binaries\Win64\`
- **目标**：归档对应目录
  - `<ArchiveDir>\<PlatformDir>\<ProjectName>\Binaries\Win64\`
  - `<ArchiveDir>\<PlatformDir>\Engine\Binaries\Win64\`
- **只处理运行时扩展名**：`.exe`、`.dll`、`.modules`、`.version`、`.so`、`.dylib`
- **排除构建产物**：`.target`、`.exp`、`.lib`、`.pdb`、`.sarif`、`.dep.json`
- **按 SHA256 比较**，只覆盖变化/新增的文件；目标缺的文件补上
- 先写 `.new` 再 `Move-Item -Force`，避免半截文件

这样：

- 今天是 monolithic → 镜像里的游戏 exe 变化 → 覆盖 exe（回退方案 B 的行为）。
- 将来切 modular → 游戏模块 DLL + `.modules`/`.version` 变化 → 只覆盖这些；引擎 DLL 不变就不动。
- 不需要为两种布局写两套代码。

### 5.2 用 `.modules` 限定模块 DLL

如果构建输出里存在 `*.modules`：

- 解析 JSON 的 `Modules` 映射（模块名 → DLL 文件名）；
- 只把映射里列出的 DLL 作为候选，不要整目录复制（`Engine/Binaries/Win64` 里有大量 editor/tool DLL）；
- 同时复制 `.modules` / `.version`（如果 hash 变了）；
- 服务器/客户端各自的 App 名不同（`UnrealGame` / `UnrealServer`），按 `*.modules` 自动识别即可。

如果没有 `.modules`（monolithic）：

- 只复制目标 exe（`<TargetName>-Win64-Shipping.exe`）；
- 以及 `Binaries/Win64` 下确实变化的运行时 DLL（tbb/D3D12/DML 一般不变）。

### 5.3 脚本 `-CodeOnly`

新增参数：

```powershell
[switch]$CodeOnly          # 只编译 Shipping + 镜像运行时二进制，不 cook/stage/pak
[switch]$ForceCodePatch    # 检测到资产/配置/Shader 变化时仍强制继续
```

流程：

1. 解析工程/target 名（现有逻辑）。
2. 校验：
   - `Platform` 必须是 `Win64`；Android 直接报“代码补丁需要重打 APK，暂不支持”。
   - `Target` 只能是 Client / Server。
   - 归档目录必须已存在（先跑过一次完整打包）。
3. 变化扫描（见 5.4）。
4. 如果 Content / Config / Shader 有变化且没给 `-ForceCodePatch` → 打印清单，`exit 2`。
5. 检查游戏/服务器进程是否在跑（`Get-Process`），在跑就报“先关掉再编”。
6. 编译：

```powershell
& $BuildBat $TargetName Win64 Shipping "-Project=$ProjectFile" -WaitMutex -NoDebugInfo -NoLinkerDebugInfo
```

- `-NoDebugInfo` + `-NoLinkerDebugInfo` 沿用现有 Shipping 编译块的组合（`Pack-CrossingVoid.ps1:1260-1278`），避免 1.6 GB pdb。
- 不传 `-build` 给 UAT；这里根本不走 UAT。
- 编辑器开着不影响（Shipping 目标不碰 Live Coding 的编辑器互斥体）。

7. 镜像运行时二进制（5.1/5.2）。
8. 覆盖后校验每个目标文件的 SHA256 与构建输出一致。
9. 写报告 `Saved\PackLogs\CodePatch\last-code-patch.json`（见 5.6）。
10. 控制台打印本次变化文件、BuildId、下一步（重算清单/碎片）。
11. `exit 0`；失败 `exit 1`；被变化检测拦下 `exit 2`。

### 5.4 变化扫描（决定“能不能只编代码”）

**基准时间**：上一次完整打包的报告

```text
Saved\PackLogs\ChunkReports\<Platform>-<Target>\latest.json → generatedAt
```

- `Quick` 报告在 `-Quick` 子目录，不能当完整打包基准。
- 没有报告时，退回归档里的 `Manifest_UFSFiles_Win64.txt` 修改时间。
- 两者都没有 → 报“没有完整打包基准，先跑一次完整打包”，`exit 1`。

扫描范围与分类：

| 类别 | 路径/扩展名 | 处理 |
|---|---|---|
| 代码 | `Source\**\*.cpp`、`Plugins\*\Source\**\*.cpp` | 允许 |
| 头文件 | `Source\**\*.h`、`Plugins\*\Source\**\*.h` | **警告**（可能动反射布局） |
| 构建配置 | `*.Build.cs`、`*.Target.cs`、`*.uproject`、`*.uplugin` | **拦截**（模块/插件结构可能变，必须完整打包） |
| 内容 | `Content\**`、`Plugins\*\Content\**` | **拦截**（需 cook） |
| 配置 | `Config\**\*.ini`、`Plugins\*\Config\**\*.ini` | **拦截**（需重新 stage/pack） |
| Shader | `Shaders\**\*.usf` / `.ush`、插件 Shader | **拦截**（需 cook） |

- 排除 `Intermediate` / `Binaries` / `Saved`。
- 每类打印前 5 个路径 + 总数。
- 拦截时 `exit 2`，提示：“检测到内容/配置/Shader/构建配置变化，纯代码补丁不安全；确认只改代码请加 `-ForceCodePatch`”。
- 头文件只警告，因为很多安全改动也会碰头；但面板要在确认框里明确写“若改了 `UPROPERTY/UFUNCTION/UCLASS/USTRUCT/UENUM` 布局，必须完整 cook”。

### 5.7 服务器 / Android

- **服务器**：同一套 `-CodeOnly -Target Server`，目标仍是 Monolithic/Unique 的 `FantasyProjectServer-Win64-Shipping.exe`；镜像到 `WindowsServer\FantasyProject\Binaries\Win64\`，然后 git 提交。服务器带宽不是问题，保持日志/控制台开关最重要。
- **Android**：代码在 APK 的 `.so` 里，纯代码补丁 = 重打 APK（还要签名/安装），不是文件覆盖；v1 禁用，tooltip 说明。以后要做就是 `Build.bat ... Android Shipping` + UAT `-package`，或者对 APK 做二进制 delta。

### 5.8 如果这次既改了代码、又新增了资产

**结论：走原本的 Patch / Base，不要走 `-CodeOnly`。**

| 变更 | 产物 | 交付 |
|---|---|---|
| 代码 | 新 Shipping exe（monolithic）或游戏模块 DLL（modular） | 启动器文件级清单（`files[]`） |
| 资产 | cook 后的 chunk pak / `_P.pak` | 文件级清单；`_P.pak` 是否可用见下 |

要点：

1. **`-CodeOnly` 会跳过 cook**：新资产不会进包，exe 和 pak 可能对不上；变化扫描应该把 Content 变更拦下来（`exit 2`），不要 `-ForceCodePatch` 硬闯。
2. **Patch 模式会自动登记未分类目录**：新增资源如果落在未覆盖目录，会登记成「版本补丁N」，有自己的 chunk；如果落在已标记目录，就跟着那个 chunk 走。
3. **代码改了反射/序列化时，Patch 的 cook 是安全网**：受影响的 cooked 资产会被重烤；这比“只编代码 + 旧 pak”安全。
4. **`_P.pak` 只是资产，不含代码**：代码永远是新 exe/DLL。不要指望 `_P.pak` 把 C++ 改动带下去。
5. **先确认启动器/游戏认不认 `_P.pak`**：你们 `GameDownloadRetrofitPlan.md` 写的是 `patches[]` 恒空、`_P.pak` 暂缓。如果还没验证 `_P.pak` 自动挂载，就不要把它当唯一资产载荷；用完整 pak 的文件级更新更稳。
6. **代码和资产必须同一次构建**：不要“先 `-CodeOnly` 编 exe，再单独补资产”，两边的时间线/序列化可能不一致。组合变更就走一次 Patch/Base，让 cook、pak、exe 都来自同一构建。

一句话：**组合变更 = 正常打包；代码补丁模式只负责“只改代码”的那条窄路。**

## 6. 安全边界：什么时候不能用纯代码补丁

### 6.1 UE 5.8 的增量 cook 能做什么

Unreal Fest 5.7《Incremental Cooking in UE 5.7》+ Epic 论坛：

- 5.8 默认启用增量 cook；它会跟踪 **class schema**、`TObjectPtr`、config 读取、asset registry 依赖等。
- 前提是 **ZenStore 存 cook 结果 + IoStore staging**；不满足时退回 LegacyIterative 或完整 cook。
- LegacyIterative **不检测 class schema 变化**，会出现“cooked 资产还是旧 schema → 运行时 Serial size mismatch / Bad export index”（Epic 论坛原帖，Matt.Peters 回复）。
- 即使是新增量 cook，也有捕获不到的依赖：自定义 `Serialize/PostLoad/PreSave`、缓存指针、管理器系统、直接读盘等；需要在 `AppendToClassSchema` 里手动声明，或对这些类型禁用增量。

**结论**：完整 cook 是安全网；纯代码补丁跳过 cook，就绕过了这层安全网。只有在“确定没有改反射布局/序列化/Shader/资产/配置”时才用。

### 6.2 安全 / 谨慎 / 禁止

| 改动 | 纯代码补丁 | 说明 |
|---|---|---|
| `.cpp` 函数体、局部变量、算法 | ✅ 安全 | 只影响模块 DLL/exe 代码 |
| `.h` 但只是注释/私有实现细节 | ✅ 基本安全 | 仍建议看一眼有没有反射宏 |
| `.h` 改了 `UPROPERTY/UFUNCTION/UCLASS/USTRUCT/UENUM` | ❌ 禁止 | 反射/序列化布局变化，cooked 资产可能崩 |
| 自定义 `Serialize/PostLoad/NetSerialize`、`FArchive` 版本 | ❌ 禁止 | 明确超出增量 cook 的自动依赖 |
| `Shaders/**/*.usf/.ush`、全局 Shader | ❌ 禁止 | 必须重新 cook shader |
| `Content/**`、`Plugins/**/Content/**` | ❌ 禁止 | 这是资产补丁，不是代码补丁 |
| `Config/**/*.ini` | ❌ 禁止 | 需要重新 stage/pack |
| `*.Build.cs` / `*.Target.cs` / `.uproject` / `.uplugin` | ❌ 禁止 | 模块/插件结构可能变；BuildId 回收的 manifest 会留旧模块 |
| 引擎升级 / 换 BuildId / 引擎 DLL 重编 | ❌ 禁止 | 新 BuildId → 全部模块要更新；走完整二进制更新 |
| 模块增删/改名 | ❌ 禁止 | 见 4.4，必须清 `.version`/`.modules` 重新生成 BuildId |

### 6.3 网络兼容

- 客户端和服务器的 C++ 代码必须同批更新；只更客户端会导致协议/序列化不一致。
- 服务器是散件/git，更新简单；但要让玩家强制更新到对应客户端版本（启动器版本号 +1）。
- 如果改了 `Replicated` 属性、RPC 签名、`NetworkVersion`，客户端/服务器必须同时发，且最好走完整包测试。

6. **插件入口/回退细节**：按钮「代码补丁（仅编译）」；是否备份上一版二进制；清单/碎片仍由发布脚本重算。
