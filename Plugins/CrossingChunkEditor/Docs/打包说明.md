# 零境交错 打包说明

## 怎么跑

```powershell
# 脚本跟着插件走：<工程>\Plugins\CrossingChunkEditor\Tools\
cd C:\CrossingVoid\Plugins\CrossingChunkEditor\Tools

# ① 快速验证：确认 chunk 打包生效（最快，先跑这个）
.\Pack-CrossingVoid.ps1 -Mode Quick

# ② 建基线：正式发布用，只做一次
.\Pack-CrossingVoid.ps1 -Mode Base -ReleaseVersion 1.0

# ③ 打补丁：改完内容后，产 _P.pak
.\Pack-CrossingVoid.ps1 -Mode Patch -ReleaseVersion 1.0
```

如果提示「禁止运行脚本」，先执行一次：

```powershell
Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass
```

（`-Scope Process` 只对当前窗口生效，关掉就恢复，不改系统设置）

工程名和 target 名不用改：脚本从工程根下的 `*.uproject` 取工程名，
再读 `Source\*.Target.cs` 的 `Type = TargetType.Game / Server` 推客户端 / 服务器 target。

## 三种模式的区别

页面上按"平时最常用"排：

| 顺序 | 模式 | 做什么 | 什么时候用 |
| --- | --- | --- | --- |
| 1 | **常规补丁更新**（Patch） | 基于基线算差异，产 `_P.pak` | 基线建好之后，每次改内容 |
| 2 | **版本更新**（Base） | 完整链路 + 建基线 | 一个新基线版本的第一次发布 |
| 3 | **快速验证**（Quick） | cook + stage（**不打 pak**），不建基线 | 只想看 chunk 生不生效 |

**Quick 和《版本更新》的差别**：Quick 不建基线、也不打 pak（产物是散件，不能发布）；
Base 会建基线并产完整 pak。两者都要经过 stage。

`-stage` 三个模式都必须有 —— pak 是从 staging 目录生成的。
Shipping 目标缺失（或源码比二进制新）时，脚本会先单独编译它，再让 UAT 带 `-nocompile` 跑。

### 「忽略缓存全量重 cook」现在是自动判断

以前菜单里有「版本更新（完全重新编译）」，得自己判断这次该用哪个。现在合并成一项，脚本在《版本更新》时自动体检：

- 扫 `Saved\Cooked\<平台>\<工程>\Content`，看有没有**工程里已经不存在的资产**（上次 cook 之后被删掉或改名的残留）
- **有** → 自动加 `-clean` 全量重 cook（约 43 分钟），日志里列出前 8 个过期文件
- **没有** → 照走增量，省时间
- 想手动强制全量：命令行加 `-Cook`

《常规补丁》**永远不参与这个判断** —— 补丁要跟基线用同一份 cook 数据，重 cook 会让差异算错。

## 查看某个 pak 里到底装了什么

UE 自带的 `UnrealPak` 可以直接列 pak 内容：

```powershell
D:\UnrealEngine-5.8.2\Engine\Binaries\Win64\UnrealPak.exe `
  "F:\DaBaoV\Crossingvoid\Windows\CrossingVoid\Content\Paks\pakchunk2-Windows.pak" -List
```

输出里两行最关键：
- `mount point "..."` —— 这个 chunk 对应哪个资源目录
- `N files (M bytes)` —— 实际装了几个文件

**排查 chunk 划分对不对，就用这个命令。**
如果 mount point 指向的目录实际有 28 个资产，但 pak 里只有 2 个，
说明 label 没圈住 —— 见下面「chunk 划分」一节。

## chunk 划分的坑：label 圈的是「引用可达集」

用 `PrimaryAssetLabel` 分 chunk 时有个经典陷阱：

**它圈的是「从 label 出发沿引用能到达的资产」，不是「某个目录下的所有文件」。**

所以会出现这种情况：

```
Cultivate_Image/ 目录实际有 28 个资产
  → 只有 Cultivate_Settle_1、_2 进了 chunk2（因为它们被别处引用了）
  → 其余 26 个没人引用 → 被当成"无主资产" → 全塞进 pakchunk0
```

**后果**：`pakchunk0` 越滚越大（零境占 99.8%），热更新粒度退化成"整个包"。
改一个贴图 → 重下 1.6 GB。

**判断方法**：用上面的 `UnrealPak -List`，对比 mount point 目录的资产数
和 pak 里的实际文件数。差得多就是没圈住。

## 容易踩的坑（都是实测撞过的）

**坑 1：`-manifests` 不能省。**
`DefaultGame.ini` 里的 `bGenerateChunks=True` 只是「允许」产 chunk，
真正让 cook 阶段产 chunk 清单的是命令行上的 `-manifests`。
少了它，就算 ini 里开着，也只出一个大 pak，不分块。

**坑 2：UE 5.8 没有 `-nochunks` 这个参数。**
在 5.3 左右的旧版本里它存在，5.8 源码里已经删了。
所以「之前关掉过 chunk」的那个开关，在新版里已经不存在了 ——
现在控制它的只有 `-manifests` 给不给。

**坑 3：`-stage` 不能省。**
pak 是从 staging 目录生成的。少了 `-stage`，UAT 会直接报：

```
Only staged builds can be paked, use -stage or -skipstage.
AutomationTool exiting with ExitCode=1 (Error_Unknown)
```

（这个坑真踩过，Quick 模式第一版就是这么挂的）

**坑 4：第一次打 Shipping 包必须编译 C++。**
编辑器只产出 Editor 目标（`CrossingVoidEditor.target`），
打包要的是 Shipping 目标（`CrossingVoid-Win64-Shipping.target`）—— 两个不同的东西。
缺了它会报：

```
Stage Failed. Missing receipt 'C:\CrossingVoid\Binaries\Win64\CrossingVoid-Win64-Shipping.target'.
Check that this target has been built.
AutomationTool exiting with ExitCode=103 (Error_MissingExecutable)
```

脚本会先单独编译目标 Shipping（收据不存在、源码比二进制新、或收据里的插件路径已失效时），
再让 UAT 带 `-nocompile` 跑 —— 不把编译交给 UAT 的 `-build`。

⚠️ 为什么不能交给 `-build`：UAT 那一轮会顺带编编辑器目标，编辑器开着时 Live Coding
持有互斥体，整批都会被拒绝。`-build` 和 `-nocompile` 也不能同时给。
脚本默认只保留 `-nocompile`，需要强制编译时用 `-ForceBuild`。

**坑 5：cook 很慢，但缓存能复用。**
零境全量 cook 实测约 **43 分钟**（2584 秒）。
cook 产物缓存在 `Saved\Cooked\Windows\`，后续打包会增量复用，不会重跑一遍。
只有加 `-Cook`（全量重 cook）才会从头再来。

**cook 慢是正常的**，不是卡死。耐心等，或者去干点别的。

**坑 6：第一次编 Shipping 要重编整套引擎，约 75 分钟。**
编辑器只编过 Development 版引擎模块，打 Shipping 包要把引擎重编一遍。
实测 863 个编译单元、**4527 秒（约 75 分钟）**。这是一次性开销。

**坑 7：编译期间日志不动，不代表卡死。**
UBA（Unreal Build Accelerator）把编译进度写进**它自己的日志**：

```
D:\UnrealEngine-5.8.2\Engine\Programs\AutomationTool\Saved\Logs\UBA-<Target>-<平台>-<配置>.txt
```

里面有真实的 `[N/863] Compile [x64] Module.XXX.cpp` 进度。

**我们脚本记的 `Saved\PackLogs\pack-*.log` 在编译期间不更新** —— 那是正常的。
想确认有没有在跑，看这两个：

```powershell
# ① dotnet 进程（UBT 是 .NET 程序，名字就叫 dotnet）
(Get-Process -Name dotnet -ErrorAction SilentlyContinue).CPU

# ② UBA 日志的更新时间
Get-Item "D:\UnrealEngine-5.8.2\Engine\Programs\AutomationTool\Saved\Logs\UBA-*.txt" |
  Sort-Object LastWriteTime -Descending | Select-Object -First 1 Name, LastWriteTime
```

**别用 `Get-Process *Unreal*` 找编译进程** —— 找不到的，UBT 叫 `dotnet`。

## 纯代码补丁（`-CodeOnly`）

只改 C++ 逻辑、没改资产 / 反射布局 / Shader / Config 时用：

```powershell
# 只编译 Shipping，把变化的 exe/DLL/.modules/.version 覆盖到归档
.\Pack-CrossingVoid.ps1 -CodeOnly -Target Client -ProjectRoot "C:\YourProject" -ArchiveDir "F:\YourArchive"

# 先看会做什么（不编译、不覆盖）
.\Pack-CrossingVoid.ps1 -CodeOnly -DryRun -ForceCodePatch -Target Client -ProjectRoot "C:\YourProject" -ArchiveDir "F:\YourArchive"
```

- 不 cook / stage / pak，不改 chunk 规则。
- 以最后一次完整打包报告为基准扫描变化；Content / Config / Shader / 构建配置变化会 `exit 2`，
  确认不需要 cook 时加 `-ForceCodePatch`。
- monolithic 时覆盖 Shipping exe；modular Shipping 时只覆盖变化的游戏模块 DLL + `.modules` / `.version`。
- Android 不支持（代码在 APK 的 `.so` 里，需要重打 APK）。
- 报告：`Saved\PackLogs\CodePatch\last-code-patch.json`。

## 参数备忘

| 参数 | 作用 |
| --- | --- |
| `-cook` | 烘焙资产（**很慢，零境约 43 分钟**） |
| `-manifests` | **产 chunk 清单（chunk 分块的真正开关）** |
| `-build` | 编译 C++（脚本默认**不传给 UAT**，改为单独编 Shipping；`-ForceBuild` 时才走它） |
| `-stage` | 组装产物目录（**pak 的前提**） |
| `-pak` | 打成 pak |
| `-compressed` | 用 ini 里的 Oodle/Kraken 压缩 |
| `-archive` | 输出到归档目录（不加就只在 StagedBuilds） |
| `-archivedirectory=<路径>` | 归档根目录 |
| `-createreleaseversion=<版本>` | 建基线，供 patch 用 |
| `-generatepatch` | 产 `_P.pak` |
| `-basedonreleaseversion=<版本>` | 基于哪个基线算差异（**必须配 generatepatch**） |
| `-nocompile` | 跳过编译检查（**不能和 `-build` 同时给**） |
| `-clean` | 全量重 cook，必须紧跟 `-cook` 后面 |
| `-Cook` | （脚本自己的开关）**强制**全量重 cook；平时由缓存体检自动决定 |
| `-ClearCache` | 只清能再生的缓存然后退出（不打包），页面上的《清除缓存》按钮走这条 |
| `-CodeOnly` | 纯代码补丁：只编译 Shipping + 镜像变化的运行时二进制；不 cook / stage / pak |
| `-ForceCodePatch` | 变化扫描发现 Content / Config / Shader / 构建配置变化时仍强制继续（危险） |
| `-DryRun` | 只列不删（配 `-ClearCache` 用）/ 只打印命令行 |
| `-CookProcessCount=<N>` | （脚本自己的开关）多进程 cook：1 个 director + N-1 个 cook worker。默认 1 = 单进程 |

## 多进程 cook（`-CookProcessCount=N`）

cook 是打包里最慢的一段。UE5.3 起 cook 本身支持**多进程并行**：把一个 cooker 拆成
「1 个 director + (N-1) 个 cook worker」好几个进程，每个进程领一批包去 cook。

开关名字就叫 `-CookProcessCount=N`，出处是引擎自己写在 `Engine\Config\BaseEditor.ini` 的注释：

```ini
; CookProcessCount sets whether we cook singleprocess or multiprocess and how many processes there should be.
; CookProcessCount=(1 or less) is singleprocess. CookProcessCount=(N>1) is 1 director and N-1 cookworkers.
CookProcessCount=1
```

UAT 的 `ProjectParams` 里**没有**这个参数（整个 AutomationTool 搜不到），所以脚本是挂在
`-AdditionalCookerOptions=-CookProcessCount=N` 上透传给 cooker 的——`-AdditionalCookerOptions`
就是 UAT 留给"往 cooker 命令行塞额外参数"的官方口子
（`AutomationTool\Scripts\CookCommand.Automation.cs` 里直接把它拼进 commandlet 参数）。

### 什么时候有用：看 profile，不看感觉

每次 cook 结束时引擎都会打一份 `Cook Profile`（在 UAT 日志里搜 `Cook Profile`）。零境最近一次
正式 cook（Win64 / Client / Base）长这样：

```
0.CookWallTimeSec=115.86
  0. 0.StartupWallTimeSec=15.43
  0. 1.CookProcessingTime=100.43
    0. 1. 2.TickCookOnTheSideTimeSec=79.28
      0. 1. 2. 0.LoadPackagesTimeSec=46.40        ← 把包载进内存：46s
      0. 1. 2. 1.SaveCookedPackageTimeSec=25.27   ← 存 cooked 包：25s
      0. 1. 2. 2.PrepareSaveTimeSec=9.59
```

**大头是「载入 + 存盘」（约 80s / 116s），不是 shader 编译**：同一次 cook 的 DDC 命中率
`TotalGetHitPct=0.999542`，shader 相关的 DDC 构建只有 MaterialShader 3.84s + GlobalShader 2.35s。
所以"想办法让 shader 编得更快"在这台机器上没有空间，把**包分给多个进程**才有空间。

### 代价（下面两条都是源码里的硬行为，不是估计）

- **CPU 是硬切的**：`CookDirector` 里 `CoreLimit = 物理核数 / 进程数`，**整除向下取整**。
  本机 8 物理核：N=4 → 每进程 2 核；**N≥5 直接掉到 1 核**，再往上加不会多给 CPU，
  只是多几个进程抢同一块。所以进程数不是"越大越好"，是"能整除才有意义"。
- **每个 worker 都是一整个 editor 进程**，而且多进程下引擎会主动**关掉"低内存就 GC"的保护**
  （`CookDirector.cpp` 的 `ActivateMachineResourceReduction()` 把 `MemoryMinFreePhysical` 设成 0、
  `MemoryTriggerGCAtPressureLevel` 设成 `Critical`）。内存不够不会优雅降级，是直接跟系统抢。
- 固定开销：每个 worker 都要启动一次引擎并载入 AssetRegistry（单进程那次 `StartupWallTimeSec=15.4`）。
  所以 cook 越短，多进程越不划算——《快速验证》那种小 cook 未必赚。

### 实测：N=5 反而慢 44%（2026-09-19）

同模式（`Base`）、同平台、同地图、都是增量 cook，可直接对账：

| | N=1 | N=5 |
| --- | --- | --- |
| `CookWallTimeSec` | 115.9 s | **180.7 s** |
| `BuildCookRun time` | 180.3 s | **259.4 s** |

日志把原因写得很清楚：

```
CookProcessCount=5. CookMultiprocess is enabled with 1 CookDirector and 4 CookWorkers.
CookMultiprocess changed number of cores from 8 to 1.
CookMultiprocess changed number of hyperthreads from 16 to 2.
loadbalanced 11247 packages across 5 CookWorkers.
  CookWorker Local/0/1/2/3: FractionOfSingleProcessCost = 0.242/0.232/0.233/0.232/0.231
```

- 每进程只剩 **1 物理核 / 2 线程** → 5 个进程一共只用 10 条逻辑线程，比单进程的 13 条还少；
- 各 worker 的 `FractionOfSingleProcessCost` 加起来 **1.170** → 多进程本身多干 17% 的活；
- 每个 worker 的 `StartupWallTimeSec` 变成 17.8 / 25.2 / 37.1 s（单进程只要 15.4 s）。

按"整除"规则，本机 8 物理核能选的值只有这些：

| N | 每进程 | 总线程 | 说明 |
| --- | --- | --- | --- |
| 1 | 8 核 / 16 线程 | 16 | 现状 |
| 2 | 4 核 / 8 线程 | 16 | 整除 |
| 3 | 2 核 / 4 线程 | 12 | 白丢 4 条线程 |
| **4** | **2 核 / 4 线程** | **16** | **唯一还值得试的值** |
| 5 | 1 核 / 2 线程 | 10 | 实测慢 44% |
| 8 | 1 核 / 2 线程 | 16 | 要同时养 8 个 editor 进程 |
| 16 | 1 核 / 2 线程 | 32 | 2 倍超订，几乎必换页 |

### 怎么开

《二游打包》页 →「运行设置（额外）」折叠区 → **Cook 进程数**（默认 1 = 单进程）。
数字框上限卡在 **4**（`SCrossingChunkPanel::MaxCookProcessCount`）——不是引擎的限制
（引擎上限是 254 个 worker），是上面那张表算出来的：本机 8 物理核，5 以上只剩负收益。
换机器（物理核数变了）时，这个常量要跟着重算。

命令行等价：

```powershell
.\Pack-CrossingVoid.ps1 -Mode Base -Platform Win64 -Target Client -CookProcessCount 4
```

开之前把编辑器关掉，然后对着两次的 `Cook Profile` 比 `CookWallTimeSec`。
数字不划算就调回 1，没有任何残留。

## 开发模式打包（Development）：让 print 打到屏幕上

「运行设置（额外）」里的勾选框决定传给脚本的 `-Configuration`。

**正式包看不到屏幕打印，不是配置没开，是那段代码根本不存在。**
`UEngine::AddOnScreenDebugMessage` 的整个函数体包在
`#if !(UE_BUILD_SHIPPING || UE_BUILD_TEST)` 里
（`Engine\Source\Runtime\Engine\Private\UnrealEngine.cpp:12468`），
蓝图 `PrintString`（`KismetSystemLibrary.cpp:534`）调的正是它。

| 配置 | 屏幕打印 | 产物目录 | 基线 |
|---|---|---|---|
| Shipping | 没有 | `<输出目录>\Windows` | `<输出目录>\Release` |
| Development | 有 | `<输出目录>\Windows`（**同一条路径**） | `<输出目录>\Release-Development` |

**产物目录不按配置分**：上传脚本（AxTools 的 `-GamePackageRoot`）认死了这条路径，
产物一挪它就静默地拿旧包去传。**基线反过来必须分**：共用 `<输出目录>\Release\<版本>\<平台>` 时，
Development 的《版本更新》（UAT 会先删了重建）会把正式基线整个覆盖掉，
之后正式线算补丁就拿了开发版当基准。

代价是两种配置的产物会挤在同一个目录里，所以脚本在**客户端**打包前会删掉另一种配置的
`exe`/`dll`（`*-Shipping.*` / `*-Development.*`，见 `Pack-CrossingVoid.ps1` 的「删掉另一种配置的二进制」段）；
pak 和资源同名，由后打的那次覆盖。**打完一种配置就顺手上传**，别混着打。

**Development 也能走《常规补丁》。** 基线按配置分开，所以
Development 里《版本更新》建基线 → Development 里《常规补丁》算差异，和正式线互不污染。三条边界：

- 补丁只带资源（pak / IoStore chunk）：改 C++ 要么重打一次 Development 包、把新 exe 一起发，
  要么回正式线走「代码补丁」（那个只做 Shipping，开发模式下按钮是灰的）。
- 非 Shipping 强制全量 cook（`Build-UatArgs` 里 `$AutoClean = ($Configuration -ne 'Shipping')`）：
  两条线共用 `Saved\Cooked`，混着用会串味。所以**客户端**的 Development 包比正式包慢。
  服务器不受这条影响 —— 它走《快速验证》分支不加 `-clean`，而且脚本本来每轮都会先删
  `Saved\Cooked\WindowsServer` 再 cook（Zen 散件的锅），换不换配置都是全量。
- 安卓没有 Development（脚本直接 `throw`）：勾选框在安卓目标下是灰的，切过去会自动关掉。

命令行等价：

```powershell
.\Pack-CrossingVoid.ps1 -Mode Patch -Platform Win64 -Target Client -Configuration Development -ReleaseVersion 1.4
```

## 服务器为什么出散件（以及 Zen 的坑）

**结论：服务器那一轮，脚本会临时把 `DefaultGame.ini` 的 `UsePakFile` / `bUseIoStore` / `bUseZenStore`
改成 `False`（已有的改值，缺的补进 `[ProjectPackagingSettings]` 段），打完自动还原。**

`DefaultGame.ini` 里通常是这样（不一定三行都显式写；没写就是引擎默认 `True`，脚本会把缺的补上）：

```ini
UsePakFile=True
bUseIoStore=True
bUseZenStore=True
```

开了 ZenStore 之后，cook 的产物**不再写成散装 `.uasset` 落在盘上**，而是流进 Zen 的 oplog；
只有 `-pak` 那一步（IoStore）才会把它物化成 `Content\Paks\*.utoc/.ucas`。而服务器这条路
从来不打 pak（要出散件给 git 用），于是 2026-09-19 实测：

| 现象 | 实测 |
| --- | --- |
| 包内文件 | 24 个（exe + 引擎 DLL + 几个字体），**没有 `Content`** |
| `Manifest_UFSFiles_Win64.txt` 列了 | 1744 条（含 `Engine/Content/Internationalization/icudt64l/*.icu`） |
| `Saved\Cooked\WindowsServer` 里 | 19 个文件 / 0.1 GB，**0 个 `.uasset`** |
| 跑起来 | 崩在 `ICUInternationalization.cpp:161 ICU data directory was not discovered` |

两个关节点：

- **cook 侧**：ZenStore 让内容只进 oplog，盘上什么都不留；
- **stage 侧**：`CopyBuildToStagingDirectory.Automation.cs:3018`
  `bStageUnrealFileSystemFiles = !CookOnTheFly && !UsePak(platform) && !ShouldTreatAsFileServer(SC)`
  —— 服务器既 `UsePakFile=True`、又因为 ZenStore 被当成 file-server，两个条件都不满足，**散件一个都不复制**。
- `bUseZenStore` 是 UAT 直接从工程 ini 读的（`ZenUtils.cs:707`），命令行没有"关掉"的开关，只能改 ini。

脚本实际做的两件事（`Pack-CrossingVoid.ps1` 的「服务器：临时把打包方式切成散件」那段）：

1. 备份 `DefaultGame.ini`（和「只 cook 勾选地图」共用同一份备份），
   把已有的键改成 `False`、缺的键补进 `[ProjectPackagingSettings]` 段；
2. 删掉 `Saved\Cooked\WindowsServer` —— 上一次是 Zen 管线，盘上只有 Metadata，
   增量 cook 会以为"已经 cook 过"从而跳过，不清就照样出不来散件（只删服务器这一份，客户端那份不动）。

打完脚本会把 ini 还原，并打印 `[配置] DefaultGame.ini 已还原`。

### 服务器和客户端不能一次打

`-Target Both` 现在直接报错退出。服务器要**关** ZenStore 才出得来散件，而客户端的分包
（`-RunChunkAssigner` 走 Zen oplog）恰恰要**开** ZenStore，两者互斥，只能分两次打。

### 归档目录：发布前自动清一次（Saved 除外）

UAT 归档**只复制、从不删**（`ArchiveCommand.Automation.cs:40-52` 的 `ApplyArchiveManifest` 里只有
`CopyFileOrSymlink`），所以上一版从工程里删掉的资源会永远躺在归档目录里 —— 走 git 的话这些
"幽灵文件"会被一起提交，也永远不会从线上消失（散件模式下引擎按路径读 `Content/`，旧资源甚至
可能还被加载到）。

所以脚本在**服务器这一轮、编译成功之后**会先把这一侧归档目录清空 —— 每次都是完整包，清掉是安全的；
放在编译之后是为了"编译失败就别动上一版的发布目录"。

**铁律：路径里任何一级叫 `Saved` 的一律不碰**（`Clear-ArchiveExceptSaved`），那是服务器的玩家数据。
删完之后 `CrossingVoid\Saved\` 会原样留着，它的父目录因为"里面还有 Saved"也不会被当成空目录删掉。
日志里会打印 `[服务器散件] 归档目录已清：删 N 项，保留 M 处 Saved`。

### 服务器走 Development（日志 + 控制台）

**决定（2026-10-21）：服务器不再往 Shipping 里塞日志/控制台，改成固定发 Development。**
`Source\FantasyProjectServer.Target.cs` 保持原样（`BuildEnvironment = Unique` 留着，但它下面没有
`bUseLoggingInShipping` / `bUseConsoleInShipping`）。面板「运行设置（额外）」里那个**开发模式**
勾选框**在服务器下不显示** —— 服务器没得选，`ResolveDevelopmentForCurrentTarget()` 直接返回 true
（不看存档：存档里若留着早先的 `0`，会静默打成 Shipping 服务器，然后开房间失败一个字日志都没有）。

| 目标 | 配置 | 为什么 |
| --- | --- | --- |
| 服务器 | **Development（固定，界面上没有开关）** | 房间的启动/回收全靠 `UE_LOG` 排查；Development 下日志、`~` 控制台、屏幕打印本来都在 |
| Windows 客户端 | Shipping（默认，可改） | 玩家不需要，也不该给玩家一个能敲命令的入口 |
| 安卓 | Shipping（固定） | 脚本直接拦 Development（`-Configuration Development` 只支持 Win64） |

**副作用（已知并接受）**：「代码补丁」只编译 Shipping（`-CodeOnly` 对非 Shipping 直接 throw），
所以**服务器永远用不了代码补丁**，按钮常灰（悬停会说明原因）。服务器改 C++ 就重打一次 Development
包、再 git 提交；确实需要 Shipping 服务器时用命令行 `-Configuration Shipping`（面板不提供）。

（客户端那边这个勾选框是初值 + 记住上次的选择，存档键 `DevelopmentBuild_Client`。）

Shipping 默认把这两样编掉，各自的依据：

| 开关 | 不开会怎样 | 依据 |
| --- | --- | --- |
| `bUseLoggingInShipping = true` | `UE_LOG` 整段被编掉，服务器崩了只留一个退出码 | `Build.h:202` `USE_LOGGING_IN_SHIPPING=0`；`UEBuildTarget.cs:6456` |
| `bUseConsoleInShipping = true` | 控制台相关的代码被编掉 | `Build.h:214/348`（`ALLOW_CONSOLE = ALLOW_CONSOLE_IN_SHIPPING`）；`UEBuildTarget.cs:6465` |

控制台那个开关只管 `#if ALLOW_CONSOLE` 那几处：`UConsole` / `GameViewportClient` 建控制台、
`APlayerController::ConsoleKey`、`SendToConsole`（`PlayerController.cpp:3956/3968`）。

**开房间不依赖它**：`CrossingSessionV1` 是在 C++ 里用 `FPlatformProcess::CreateProc` 拉进程
（`CrossingVoidSessionManager.cpp:240`），走的是 Win32 进程创建，不是控制台命令。
蓝图 `Execute Console Command` 节点在 Shipping 里也没被编掉（`KismetSystemLibrary.cpp:571`）。
所以这两个开关对"能不能开出房间"没有影响，只影响"出问题能不能看见"。

**这就是为什么服务器固定 Development**：`CrossingVoidSessionManager.cpp` 里那几条 `UE_LOG`
（`:158` StartSessionService 失败、`:237` launching room、`:254` CreateProc failed）在 Shipping 里
会被整段编掉 —— 开房间失败时，日志里一个字都不会有，只剩退出码。走 Development 就不用改
`.Target.cs`（改了会触发整目标全量重编，见下节），日志天然就有。

客户端那边一直是不开的（`CrossingVoid.Target.cs` 里留了注释就是防止以后被顺手加回来）：
客户端只负责把信号发给服务端，开了等于给玩家一个能敲命令的入口（Windows 上按 `~` 就出来）。

## 什么时候会全量重编（以及为什么不是"打包指令变了"）

2026-10-20 那次 Shipping 又要编 800 多个文件，第一反应是"打包命令改了"。**不是。**
UBT 日志把原因写得很直白（`Engine\Programs\UnrealBuildTool\Log.txt`，以及同目录的 `Log-backup-*.txt`）：

```
FantasyProjectServer.Target.cs has been modified since makefile was written.
HashSHA256.uplugin has been added
Invalidating makefile for FantasyProjectServer (source file added)
```

UBT 对"target 的构建输入"变化是**整目标作废**：`.Target.cs`、项目里增删插件/模块一变，该 target
的 makefile 就失效，它名下**所有** C++ 全部重跑 —— 跟你改了几个文件无关。更狠的一条：
**任何一个 `.Target.cs` 改动会让所有 target 失效**（实测 15:14 改的是服务器的 Target.cs，
日志里连 `FantasyProjectEditor` 的 makefile 一起被作废）。

所以：

- 改 `.Target.cs`（日志/控制台开关、BuildSettings）→ 所有 target 全量。**一次调完**，别反复改。
- 往 `Plugins\` 里加/删插件 → 全量。加插件本身值这个价，但别在打包当天加。
- `Config\DefaultGame.ini` 变动只实测到作废 **编辑器 + ShaderCompileWorker** 的 makefile
  （生效点：`has been modified since makefile was built`）；16:35 那次服务器 Shipping 构建
  **没有**把它列为失效原因，说明它不影响 game/server target。

被打断过一次的真实代价：那次 16:35 跑到第 22 个 obj 就断了（日志停在 `[20/729]`，没有 `Result:` 行），
中间产物半新半旧、makefile 已作废 → 下次还是从头。**别在中途停**，让它一次跑完，之后就是增量。

## 清缓存（腾磁盘）

页面《二游打包》→「运行设置（额外）」→「工具」里的 **《清除缓存》** 按钮，命令行是同一条：

```powershell
.\Pack-CrossingVoid.ps1 -ClearCache

# 只想看会清掉多少、不动手
.\Pack-CrossingVoid.ps1 -ClearCache -DryRun
```

只删这三样（都能自动重建）：

| 目录 | 是什么 | 删了之后 |
| --- | --- | --- |
| `Saved\StagedBuilds` | UAT 组装的产物 | 下次打包重新组装 |
| `Saved\Cooked` | cooked 数据 | 下次 cook 从头来（慢一些） |
| `Saved\Shaders` | shader 缓存 | 下次重新编译 shader |

脚本里还有一层兜底：删之前解析真实路径，不在工程内的直接拒绝。

## 基线存在哪

```
<输出目录>\Release\<基线版本>\<平台>\
```

比如输出目录是 `F:\DaBaoV\Fantasy`，基线就在
`F:\DaBaoV\Fantasy\Release\0.1\Windows\`（客户端）。

这个根目录**跟随输出目录 + 当前配置**，不再单独配置：
插件里「运行设置（额外）→ 基线位置」是**只读**的，值自动派生 ——
Shipping 是 `<输出目录>\Release`，Development 是 `<输出目录>\Release-Development`
（产物目录两种配置共用同一条，基线必须分开，否则开发包的《版本更新》会覆盖正式基线）；
脚本参数 `-ReleaseRoot` 留空时也按这个规则算。
建基线（写）和算补丁（读）走的都是这一个值，换工程不会还指着上一个工程的旧路径。

基线里装的是**那一次打出来的 pak 容器本体**（`.pak` + `.sig` + IoStore 的 `.utoc`/`.ucas`），
大小 ≈ 那次所有 chunk 容器之和（客户端约 1.5 GB）。UAT 源码原话：
`copy the created pak to the release version directory we might need this later if we want to generate patches`

**放在输出目录同一个盘**——基线可能有 1.5 GB，别放系统盘；跟着输出目录走也方便整体迁移。

**这个目录别乱删** —— 删了以后所有基于它的 patch 都算不出差异。

《版本更新》的语义就是"**更新 / 重建基线**"：同一个版本号再跑一次 = **重建它**，
旧基线会**直接删掉**（删之前校验路径确实在基线根目录里，防止拼错删到别处），
所以不需要你手动去翻目录清理。

## 两个"版本号"不是一回事

|  | 玩家版本 | 基线版本 |
| --- | --- | --- |
| 给谁看 | 玩家（APK 应用信息里显示的那个） | 只有打包流程 |
| 存在哪 | `Config\DefaultEngine.ini` → `AndroidRuntimeSettings.VersionDisplayName` | `<输出目录>\Release\<号>\`（根目录自动派生、只读，不用手工配） |
| 什么时候改 | 每次发版想改就改 | 每次《版本更新》换一个新号 |
| 页面上的取值 | 你填 | **由玩家版本自动推出来，只读不能改**：`0.5.13` → `0.5` |

`StoreVersion`（versionCode）刻意保持 1 不动。一条基线覆盖它下面所有小版本的补丁：
玩家版本 `1.4.2` / `1.4.5` 都基于基线版本 `1.4`，不用每次重建基线。

## 日志

每次打包的完整输出：
```
<工程>\Saved\PackLogs\pack-<模式>-<平台>-<时间戳>.log
```

pak 清单：
```

```

出了错先看日志，grep 里头的 `Error` 和 `Warning`。

### 客户端自己的日志（Shipping 也有）

打包出来的客户端**以前一个字都不写**，因为 Shipping 默认把日志整个关掉：
`Core\Public\Misc\Build.h:202` 是 `#define USE_LOGGING_IN_SHIPPING 0`，
`UEBuildTarget.cs:6458` 只有开了 `bUseLoggingInShipping` 才会加 `USE_LOGGING_IN_SHIPPING=1`。
所以那时候 `-ABSLOG=` / `-LOG=` 都没用（日志设备根本没建），双击没反应就只能看到一个退出码 1。

已经在 `Source\CrossingVoid.Target.cs` 里打开：

```csharp
bUseLoggingInShipping = true;
```

现在 Shipping 客户端会写到：

```
%LOCALAPPDATA%\CrossingVoid\Saved\Logs\CrossingVoid.log
```

（`%LOCALAPPDATA%\<项目名>`，不是包目录里的 `Saved` —— 打包后的游戏用用户目录。）
代价：这个属性带 `[RequiresUniqueBuildEnvironment]`，第一次开要重编一次该目标。

想再进一步（让 Shipping 里的 `check()` 也生效、崩了能直接看到断言），可以再加
`bUseChecksInShipping = true;`。默认没开 —— 它会让线上也硬崩，现在是开发期可以按需加。

### 客户端二进制会不会「过期」

**会，而且非常隐蔽**：打包脚本一律给 UAT 传 `-nocompile`（`-build` 会顺带编编辑器目标，
撞 Live Coding），Shipping 目标由脚本自己单独编。而"要不要编"以前只看收据
`Binaries\Win64\<目标>-Win64-Shipping.target` 在不在 —— **收据在就跳过编译**。

2026-09-19 的翻车就是这个：收据是 9/18 编的，`DreamChunkDownloaderSubsystem.cpp`
9/19 16:56 改过（启动时加载 build manifest 的 ticker 崩了，改成弱指针），
脚本看收据在 → 不编 → 打出来的客户端里是**一天前的旧二进制** → 双击直接崩。
同理，那种"改了 C++ 但没重编，打包却一路绿灯"的情况都属于这一类。

现在改成按时间戳判：**源码（`Source\` 与 `Plugins\*\Source\` 下的 cpp/h/cs/uplugin，
排除 Intermediate/Binaries/Saved）比 Shipping 二进制新就要编**，并且会打印是哪个文件触发的。
只会多编一次（编完二进制就比源码新了）。`-DryRun` 下只会打印"本应编译：<原因>"，不会真编。

## 版本号（内容版本 / 网络兼容版本分开）与旧包自检

**面板的「玩家版本」= 内容版本。** 打包时脚本写两处：
`Config\DefaultGame.ini` 的 `[CrossingVersion] GameVersion`（全平台，运行时读得到）
+ `Config\DefaultEngine.ini` 的安卓 `VersionDisplayName`（商店/系统显示）。
游戏侧读法：`UCrossingVersionLibrary::GetGameVersion()`（蓝图节点「提取内容版本」所在库）。

**刻意不写 `GeneralProjectSettings.ProjectVersion`** —— 它是网络兼容性版本：

```
Config\DefaultGame.ini → GeneralProjectSettings.ProjectVersion
  ↓ UnrealEngine.cpp:2539  // "Make sure networking checksum has access to project version"
  FNetworkVersion::SetProjectVersion(ProjectSettings.ProjectVersion)
  ↓ NetworkVersion.cpp:241
  网络版本 = CRC32("工程名 + ProjectVersion + 引擎 NetCL + 网络协议版本")
  ↓ NetworkVersion.cpp:263
  IsNetworkCompatible(L,R) => L == R        ← 严格相等
  ↓ World.cpp:7381 / NetConnection.cpp:1341
  不等 → 服务端 NMT_Upgrade → 客户端 ENetworkFailure::OutdatedClient → Close
```

所以它是"**硬拦**"：旧客户端在 connect 阶段就被引擎拒连，**看不到任何提示，也走不到你登录界面的版本校验**。
只在真的改了网络协议/包结构（老客户端进新服会出问题）时才手动抬它；日常发版改 `GameVersion` 即可。

> 写 `GameVersion` 的那段代码**必须排在"临时改写 DefaultGame.ini"之前**（地图清单那一步是
> "备份 → 改写 → 打完还原"，写在后面会被还原掉，等于没写）。

### 旧包为什么会拿新号

2026-10-26 的事故：碎片生成拿的源目录 `H:\DaBaoV\Crossingvoid\Android` 里，APK/OBB 都停在
**10-11 23:22**、`CrossingVoid.version.json` 还是 **0.6.0**，但这次发布用了新版本号。
整条链路没有任何一处会报错 —— 于是"新号发了旧包"。

### 现在怎么防

1. 打包成功后写版本戳（2026-10-28 起，不再写旧的 `Version.json`）。按「平台-目标-配置-模式」
   各一套，目录是 `<归档根>\Version\<Scope>\`（Scope = `Win64-Client` / `Android-Client` /
   `Win64-Server-Quick` / `…-Development` / `…-Quick`），里面三份：
   `Version-Full.json`（整包，`kind=Full`）、`Version-Patch.json`（补丁，`kind=Patch` + `baseVersion`）、
   `Latest.json`（指针：`latestFile` / `generatedAt` / `pluginVersion`）。
   Windows / 安卓 / 服务器互不覆盖，也不在 `Windows`/`Android` 子目录里（不会被启动器一起发布）。
   `files[]` 每项是 `path`（相对归档根的 posix 路径）+ `sizeBytes` + `sha256` + `modified`；
   版本包（`Base`）列发布目录全量（排除 pdb/Symbols/win-x64），补丁和快速验证只列本次产出的关键产物。
   `latestFile` 是相对归档根的路径；发布那边不用再扫一遍算哈希；
2. 发布前跑 `Tools\Test-PackageVersion.ps1 -ArchiveDir <归档根> -ExpectedVersion <版本>`
   （再加 `-Platform Android -Target Client -Configuration Shipping` 定位对应 scope；
   只给 `-Platform` 也行，不传就自动用 `Version` 下唯一那套）：
   没有 `Latest.json` / 指针指向的文件不存在 / 版本不一致 / 戳超过 24 小时 / 是《快速验证》产物 /
   补丁没有 `baseVersion` / 清单里的文件缺失或大小不符 → 全部 `exit 1`。
   补丁再加 `-ExpectedBaseVersion <基线>` 判断是否"在旧基线上打的补丁"；
   加 `-ExpectedNetworkVersion 1.0.0` 可以顺带核对"连不连得上"——**客户端包和服务器包这一项必须一致**
   （记录在版本戳的 `networkVersionEffective`；`networkVersionSet:false` 表示没显式设置、引擎退回 1.0.0）。
   排查"旧包连不上"时先比这一项，比内容版本有用得多；
3. 面板「运行设置（额外）→ 工具 → 版本自检」就是它；旁边的「产物目录」直接打开要给碎片生成的
   那个目录，省得手输指到旧路径（根因八成在这里）。

> DryRun 现在真的"只看不干"：安卓版本号那段以前不看 `-DryRun`，侦察一次就顺手把工程里的
> `VersionDisplayName` 改了（2026-10-27 干跑时踩到：0.1.1 被写成 0.6.1）。两段版本写入现在都先判 `-DryRun`。

## pdb 与符号文件（为什么产物里没有 pdb）

**结论：Windows 的 Shipping 包本来一定会产 pdb；要关掉必须两个开关一起给
（`-NoDebugInfo` + `-NoLinkerDebugInfo`），缺一个都不行。**

| 产物 | pdb | 大小 |
| --- | --- | --- |
| 客户端 | `CrossingVoid-Win64-Shipping.pdb` | 约 1.6 GB |
| 服务器 | `CrossingVoidServer-Win64-Shipping.pdb` | 约 1.5 GB |

它们本来会跟着归档目录一起走 —— UAT 把它们归到 `StagedFileType.DebugNonUFS`，
也就是上面提到的 `Manifest_DebugFiles_Win64.txt`。

### 为什么"不想要"还得专门关两刀

引擎在 Windows 上是**两段式**，只看一段会得出错误结论（我们就是这样先错了一次）：

**① 编译期**——`UEBuildPlatform.cs:1367-1369`

```csharp
GlobalCompileEnvironment.bCreateDebugInfo =
    Target.DebugInfo != DebugInfoMode.None && ShouldCreateDebugInfo(Target);
GlobalLinkEnvironment.bCreateDebugInfo = GlobalCompileEnvironment.bCreateDebugInfo;
```

关键：`ShouldCreateDebugInfo(Shipping)` 返回 `!bOmitPCDebugInfoInDevelopment`，
而那个开关**默认是 false**（而且只有 `[XmlConfigFile]`，命令行给不了）
→ **Shipping 的编译期调试信息默认是开的** → 链接期一开始就抄到 `true`。

**② 链接期**——`UEBuildWindows.cs:2175-2184`：

> 原文："NOTE: Even when debug info is turned off, we currently force the linker to generate debug info anyway on Visual C++ platforms. This will cause a PDB file to be generated with symbols for most of the classes and function/method names, so that crashes still yield somewhat useful call stacks..."
>
> ```csharp
> if (!Target.WindowsPlatform.bNoLinkerDebugInfo)
> {
>     GlobalLinkEnvironment.bCreateDebugInfo = true;
> }
> ```

这句是**"不再强制打开"**，不是"关掉"——它管不了 ① 已经打开的 `true`。

**所以：**

| 给什么 | 编译期 | 链接期 | pdb |
| --- | --- | --- | --- |
| 什么都不给 | true | true | **有** |
| 只给 `-NoLinkerDebugInfo` | true | true（抄来的） | **还是有** ← 我们踩过的坑 |
| 只给 `-NoDebugInfo` | false | true（被 ② 强制打开） | **还是有** |
| 两个都给 | false | false | **没有** ✓ |

> 实测：2026-09-19 14:26 那次服务器打包只带了 `-NoLinkerDebugInfo`，
> 结果 `CrossingVoidServer-Win64-Shipping.pdb` 照样产出了 1544.6 MB。

### 这个开关的完整链路（在 5.8 源码里逐环验证过，不是猜的）

| 环节 | 源码位置 | 说明 |
| --- | --- | --- |
| 开关本体 | `Platform\Windows\UEBuildWindows.cs:698-703` | `[XmlConfigFile(Category="WindowsPlatform")]` + `[CommandLine("-NoLinkerDebugInfo")]`，默认 false |
| 命令行怎么进去 | `Configuration\Descriptors\TargetDescriptor.cs:380` → `Configuration\Rules\TargetRules.cs:3362-3367` | 目标描述符携带整条命令行，之后 `Arguments.ApplyTo(WindowsPlatform)` |
| 能不能写 ini | **不能** | 该字段只有 `[XmlConfigFile]`（对应 BuildConfiguration.xml），没有 `[ConfigFile]`，写进 `DefaultEngine.ini` 无效 |
| 链接器侧 | `Platform\Windows\VCToolChain.cs:1738-1749, 3493-3510` | 只有 `bCreateDebugInfo` 为真才加 `/DEBUG:FULL` 和 `/PDB:` |
| 归档时会不会报错 | `AutomationUtils\DeploymentContext.cs:1029-1035` | 注释原文 "Symbol files aren't true dependencies so we can skip if they don't exist" —— 没有 pdb 就静默跳过 |

### 我们脚本的做法

`Pack-CrossingVoid.ps1` 默认给 Windows 的 Shipping 目标加**两个**开关：

- 独立编译那一步：`Build.bat <目标> Win64 Shipping -Project=... -WaitMutex -NoDebugInfo -NoLinkerDebugInfo`
- **代价**：`-NoDebugInfo` 改了编译参数 → 该目标要**全量重编一次**（编完中间物也会变小）
- **只在这一步加**，不给 UAT 传 `-ubtargs`：`-ForceBuild` 时 UAT 那一轮
  （编辑器目标也在一起）是整轮生效的，会把 Rider 调试用的编辑器 pdb 一起干掉
- 归档之后仍然兜底扫一遍 `*.pdb` 再删（防的是「复用旧 exe / 旧 pdb」——
  打包默认 `-nocompile`，本来就不会重新链接）

想保留 pdb 就加 `-KeepSymbols`：那时不加这个参数，归档也保留。

### Development 配置也一样（服务器改走 Development 之后的确认）

**结论：服务器打 Development 也**不会**产 pdb。** 三条依据：

1. **脚本的编译开关是配置无关的**：`Pack-CrossingVoid.ps1:1802` 用 `$Configuration` 拼目标，
   `:1819` 无条件追加 `-NoDebugInfo -NoLinkerDebugInfo`（只受 `-KeepSymbols` 控制）。
   Shipping 和 Development 拿到的是同一套开关。
2. **UBT 里 Development / Shipping / Test 走同一个分支**（`Platform\Windows\UEBuildWindows.cs:2192`）：

   ```csharp
   case UnrealTargetConfiguration.Development:
   case UnrealTargetConfiguration.Shipping:
   case UnrealTargetConfiguration.Test:
       return !Target.bOmitPCDebugInfoInDevelopment;   // -NoLinkerDebugInfo 把它置 true
   ```

   注意 **Development 和 Shipping 在这件事上完全等价** —— 网上"换 Development 少产符号"的说法不成立，
   不给开关时两者都会产 pdb。
3. **归档兜底按扩展名扫**（`:2054-2065`，只删 `*.pdb`，不看配置名），所以就算哪天冒出一个
   `*-Win64-Development.pdb` 也会被剔除。

旁证：`Binaries\Win64\` 里两个 Shipping exe（2026-10-19）旁边都没有 pdb，只有 9/1 的编辑器 pdb。

> 别混：日志/控制台（`USE_LOGGING_IN_SHIPPING` / `ALLOW_CONSOLE`）和 pdb（`DebugInfo` / 链接器 `/DEBUG`）
> 是两套独立开关。服务器 Development 有日志，但没有符号 —— 要符号化崩溃得用 `-KeepSymbols`，且 pdb 只留本地。

### 唯一的副作用

关掉之后链接器不再产任何调试信息，于是：

- 崩溃栈只有「模块名 + 偏移」，没有函数名和行号。
- 本地 `C:\CrossingVoid\Binaries\Win64\` 里现在那两个老 pdb（1.6 GB + 1.5 GB）是
  **上一次构建**留下的，跟以后编出来的 exe 对不上，留着也没用；确认不需要就删掉，省 3.2 GB。
- 以后若想能符号化服务器崩溃：用 `-KeepSymbols` 打包，并且那份 pdb **只留本地**（别进包、别进 git）。

> 出处：知乎《UE4/5 客户端崩溃分析》（https://zhuanlan.zhihu.com/p/1891179882790253014）
> 原文摘要："打包时提示缺少PDBCOPY.EXE无法剥离符号，是因为Windows SDK组件缺失了Windows Debugging Tools，安装对应组件即可正常完成符号剥离，大幅压缩安装包体积。对于已经打包完成的版本，手动删除对应输出目录中的 `.p[db]`"
> 我们的验证：引擎源码 `Automation\Win\WinPlatform.Automation.cs:670-677` 确实在找不到 `pdbcopy.exe` 时直接抛 `AutomationException` —— 证实「剥离符号」这条路依赖 Windows Debugging Tools。所以我们不走剥离、也不事后手删，而是从源头不生成（顺带省掉 1.5 GB 的写盘和链接时间）。
> 中文社区里的常见做法只有三种：剥离、手动删、换 Development 少产符号；`bNoLinkerDebugInfo` 这个开关在知乎站内搜索里 0 条命中，是读 5.8 源码得到的。

## 关掉 ZenStore 会发生什么（能不能不用 Zen）

**结论：Zen 不能关** —— 不是"关了会崩"，而是**分块链路直接断**：`-RunChunkAssigner` 需要 cook 写进 Zen 的 oplog（项目存储）。

证据（`Engine\Source\Programs\AutomationTool\Scripts\OplogChunkAssigner.Automation.cs` 的 `RunFromStagingContext`）：

```csharp
if (string.IsNullOrEmpty(SC.PackageStoreData.ZenServerStore.ProjectId) || string.IsNullOrEmpty(SC.PackageStoreData.ZenServerStore.OplogId))
    throw new AutomationException("SC.PackageStoreData.ZenServerStore must be loaded before performing chunk assignment. Ensure LoadPackageStoreData was called.");
```

`bUseZenStore=False` 之后 oplog 不存在 → assigner 拿不到 `ProjectId/OplogId` → **staging 阶段直接抛异常**，不是"分块不准"。所以要真的"不用 Zen"，必须三件事一起改：

1. `Config/DefaultGame.ini` → `bUseZenStore=False`（cook 落盘，不再进 Zen）；
2. **去掉** UAT 的 `-RunChunkAssigner`（脚本里的 `-SkipChunkAssigner`）；
3. 分块**完全依赖** `Config/DefaultPakFileRules.ini`（由 `Build-PakFileRules.ps1` 从 `DefaultCrossingChunk.ini` 生成，当前 84 条目录规则 + 1 条兜底）。

| | Zen 开（现状） | Zen 关 |
|---|---|---|
| 分块依据 | oplog assigner（精确到资产） | 目录规则（`+Files=` 通配） |
| 规则没覆盖到的资产 | assigner 仍能分对 | **落进 chunk 0**（基础包变大） |
| cooked 数据 | 进 Zen（`Saved\Cooked` 只剩元数据） | 落盘（`Saved\Cooked` 几万个文件） |
| 增量 cook | 不可用（无本地缓存） | **可用**（`-forcerecook=false` 才有意义） |
| 打包耗时 | 每次全量 cook（11k+ 包） | 首次全量，之后增量 |
| 磁盘 | Zen CAS 占用 | `Saved\Cooked` 占用 |
| 本次这类故障 | 会复发（UAT→Zen 的 oplog 请求失败） | 不复存在（不依赖 oplog） |

另一条**已验证**的经验：服务器目标本来就关 Zen（散件必须落盘），脚本里"临时把 `UsePakFile / bUseIoStore / bUseZenStore` 改成 False"就是干这个；但它同时也去掉了 `-manifests` / `-pak` / `-RunChunkAssigner`，所以服务器根本没有"分块"这回事。

### 2026-10-27 排障记录（重要）

现象：cook 成功（`ExitCode=0`），到 staging 报

```
Zen server is not running at [::1]:8558. ...
Failed sending oplog request to Zen at [::1]:8558: ZenServer is not running (or is not responding),
even after attempting to AutoLaunch (3 attempts).
```

但 Zen 本身是健康的：`GET http://[::1]:8558/health/ready` = **200**，`/prj/CrossingVoid.ba5ac229/oplog/Windows` = **200**，Zen 日志里失败时刻**没有任何 oplog 请求记录** —— 请求根本没到 Zen。

排查过的无效手段（别再重复）：

| 试过 | 结果 |
|---|---|
| 重启 Zen / 换新实例 | 无效 |
| 清 Zen 工程数据 + `Saved\Cooked\Windows` + `StagedBuilds` | 无效 |
| 去掉 `-forcerecook=false`（全局 cook 增量化） | 无效 |
| `-SkipChunkAssigner` | 无效 —— staging 仍要 `Reading oplog from Zen...` |
| 还原插件到旧版本 | 无效（失败那次的 UAT 命令行与成功那次逐字相同） |

有效手段（按代价排序）：

1. **让 cook 用 IPv4 连 Zen**：UAT 参数 `-NoZenAutoLaunch`（本插件脚本里的 `-ZenIPv4` 开关）。
   assigner 的地址取自 cook 写进 `Saved\Cooked\Windows\ue.projectstore` 的 `host:port`，
   用 IPv4 连 Zen 会把它记成 `127.0.0.1:8558`，assigner 也就走 IPv4；
2. 或者彻底走上面"不用 Zen"的方案（关 ZenStore + 去 `-RunChunkAssigner` + 规则分块）。

### 已确认（2026-10-27 15:11）

`-ZenIPv4` 方案**验证通过**：同一个工程、同样的参数，只把 Zen 地址从 `[::1]` 换成 IPv4，打包直接成功。

```
Zen:      127.0.0.1:8558, project=CrossingVoid.ba5ac229, oplog=Windows
Reading oplog from http://127.0.0.1:8558/prj/CrossingVoid.ba5ac229/oplog/Windows/entries
```

因此脚本现在**默认**就给 UAT 加 `-NoZenAutoLaunch`（即用 IPv4 连 Zen）；真要 IPv6 才加 `-ZenIPv6`。

判断方法看一行日志就够：staging 阶段的 `Zen:` 后面如果是 `127.0.0.1:8558` → 正常；是 `[::1]:8558` → 大概率会挂。
